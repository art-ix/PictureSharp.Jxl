# Extra channels for 0.8.16

Status: implemented (2026-11-02), not committed; decisions 1a, 2a, 3a, 4a (user). Base: `7ae2aa9` (0.8.15 + README).

0.8.16 is the last step of the feature series (roadmap in plan.md: 0.8.10 blending, 0.8.11 layers, 0.8.12 animation
decode, 0.8.13 frame reader, 0.8.14 animation encode, 0.8.15 noise and splines, 0.8.16 extra channels, 0.8.17
hardening, 0.9.0). JPEG XL images may carry extra channels next to colour: alpha (straight or premultiplied), spot
colours (an ink with its own colour and opacity), black (the K of CMYK), and channels with no visual meaning (depth,
selection mask, thermal, colour filter array, optional, unknown and reserved types).

Goal: `Image.Load`, `Image.Identify`, `Image.OpenFrameReaderAsync` and `JxlLayers` decode images with premultiplied
alpha and spot colours as djxl 0.12.0 does (premultiplied alpha returned as straight alpha, spot colours rendered into
the colour), and images with other extra channels by decoding and dropping those channels. Results are identical at
1 and N threads, and every existing result stays unchanged. Black (CMYK) and float samples stay
`NotSupportedException`, now naming the missing PictureSharp core support. No core change and no public API change.

## What exists

- `IO/JxlExtraChannelInfoReader` reads every extra channel type with its fields (`AlphaAssociated`, `SpotColor`,
  `Cfa`, name, bit depth, `DimShift`). The encoder writes alpha only.
- `Frames/JxlDecodeSupportPolicy.EnsureImageSupported` throws for Black and SpotColor channels ("… extra channels are
  not decoded yet."), for float or premultiplied alpha, and for any float extra channel. Every other type (Depth,
  SelectionMask, Thermal, Cfa, Optional, Unknown, Reserved) already passes: such channels are decoded, upsampled,
  patched and blended like every extra channel, and only the first alpha channel reaches the output. No corpus file or
  test covers them.
- `JxlBlending` and `JxlPatches` already handle premultiplied alpha in Blend/AlphaWeightedAdd (`AlphaAssociated`,
  0.8.10), so the canvas of a premultiplied image is correct in premultiplied form.
- `JxlImageInfoMapper` reports `ImageAlphaMode.Premultiplied` for associated alpha and `ImageColorModel.Cmyk` for a
  Black channel (`ImageColorInfo` describes the stored samples).
- Output: `JxlPixelWriter` writes straight-alpha `Rgba32`/`Rgba64` from three paths: float planes, integer samples of
  plain lossless frames (`JxlIntegerImage`) and the deferred YCbCr rows (`JxlColorRows`, 0.8.6).
- `JxlDecodeSession.Iterate`: the still path (`JxlFrameDecoder.Finish`), the per-frame still path of animations, the
  blended/copied canvas path (`RenderColor`, `Blend`/`Copy`, `Output`), frames stored before the colour transform
  (`Store`), and the layer sink of `JxlLayers` (`Layer`). With `ColorConversion = ToSrgb`, XYB stills render straight
  to sRGB and canvases are converted by `JxlCanvasToSrgb` after blending.
- Conformance corpus (ignored, `tests/assets/external`): `alpha_premultiplied` (VarDCT, 12-bit colour, 16-bit
  premultiplied alpha), `alpha_nonpremultiplied`, `spot` (Modular, 16-bit ProPhoto ICC, alpha + two spot colours,
  two layers) and `cmyk_layers` (Black).

## What libjxl does (v0.12.0)

### Premultiplied alpha (alpha.cc, render_pipeline/stage_write.cc, dec_frame.h)

- The decoder keeps colour premultiplied through the whole pipeline (blending treats it as associated). Only the
  output stage unpremultiplies, and only when the API asks for it (`JxlDecoderSetUnpremultiplyAlpha`, default off) and
  the **first** alpha channel (`Find(kAlpha)`) has `alpha_associated` (`SetImageOutput`).
- `WriteToOutputStage::UnpremulAlpha`: per pixel `mul = 1 / max(kSmallAlpha, alpha)` with `kSmallAlpha = 2^-26`,
  then each colour channel (one for gray, three for colour) `× mul`, in the output colour space (after the colour
  transform, blending, spot colours and colour management), right before the float → 8/16-bit conversion with its
  clamping and dithering. Alpha itself is unchanged. `UnpremultiplyAlpha` in `alpha.cc` is the same formula.
- So a pixel with alpha 0 and colour 0 stays 0 (exact premultiplied data, lossless). A lossy file whose colour is
  slightly above 0 where alpha is 0 or tiny gets that colour multiplied by up to 2^26 and clamped (decision 1).
- djxl 0.12.0 never sets the option (`extras/dec/jxl.h`: `unpremultiply_alpha = false`, no command-line flag): its PNG
  and PAM output of such files is premultiplied (decision 2).

### Spot colours (render_pipeline/stage_spot.cc, dec_cache.cc `PreparePipeline`)

- With `render_spotcolors` (the decoder default, and djxl's unless `--norender_spotcolors`), one `SpotColorStage` per
  spot channel, in extra-channel order: `mix = spot_color[3] × s`, then for c in 0..2:
  `p[c] = mix × spot_color[c] + (1 − mix) × p[c]` (s = the spot channel's sample, `spot_color` = the four F16 values of
  the channel info: colour and opacity). No clamping.
- Position: after the colour transform stage (YCbCr → RGB, or XYB → linear), after blending and after the frame is
  saved for reference (`save_before_ct` false), before tone mapping, the linear → transfer function stage or the CMS,
  and before the output stage (so before unpremultiplying). Consequences:
  - XYB frames that need no blending (a full frame that replaces, or every layer with coalescing off): the mix happens
    in **linear** light of the output primaries (libjxl's XYB stage already includes the primaries; with an ICC profile
    it is linear sRGB, converted by the CMS afterwards).
  - XYB frames that blend (coalescing on): `FromLinear` runs before blending, so the mix happens in the output's
    transfer function, on the blended canvas.
  - Other frames (Modular RGB, YCbCr): in the coded colour space after the colour transform; with blending on the
    blended canvas.
  - The reference slot keeps the colour without spot colours (the spot channels themselves are kept in the slot as
    extra channels and blended like any extra channel), so later frames blend onto colour without ink and the ink
    is rendered again on every displayed frame.
- Gray images have three colour channels in the pipeline, all equal; the gray output takes channel 0, so the result
  is the mix with `spot_color[0]`.

### Other types

- Depth, SelectionMask, Thermal, Cfa, Optional, Unknown, Reserved0–7: decoded (they have to be, as the Modular
  stream interleaves them), upsampled, patched and blended, and never written to the colour output. djxl writes them
  nowhere unless asked for extra-channel outputs.
- Black: `PreparePipeline` adds a CMS stage that needs a CMYK ICC profile (CMYK → RGB through the CMS). Float samples:
  converted from their bit patterns to floats (`exponent_bits_per_sample`).

## Design

### Support policy

1. `EnsureImageSupported` throws only for:
   - Black channels: "JPEG XL: CMYK images (a Black extra channel) need colour management for CMYK profiles, which
     PictureSharp does not provide yet." (`ImageColorModel.Cmyk` from Identify stays.)
   - float colour, float alpha or any float extra channel: "JPEG XL: floating-point samples need a float pixel type,
     which PictureSharp does not provide yet." (user decision 2026-11-01: float extra channels included, also those
     that would be dropped.)
   Premultiplied alpha and spot colours no longer throw. Only the first alpha channel is the output alpha (as now);
   further alpha channels are dropped like libjxl.
2. `JxlLayerCollector`/`JxlLayerStack` keep their rules; they get no new extra-channel rejections.

### Premultiplied alpha

3. The decoded image (`JxlDecodedImage`) gets `Premultiplied` (the first alpha channel is associated). The planes,
   integer samples and deferred rows stay premultiplied; `JxlPixelWriter` unpremultiplies each row right before it is
   written, in every path: float plane rows are copied to per-worker rows, integer rows are unpremultiplied after
   scaling (the rows already exist), deferred YCbCr rows after rendering. Formula exactly as `UnpremulAlpha`
   (`1f / MathF.Max(2^-26, a)`, then one multiply per colour sample; decision 1), gray on the gray sample only. So
   8-bit dithering, `Rgba64` and the frame reader all see straight values. A `.Simd.cs` version only with a measured
   gain.
4. The canvas, reference slots, blending and patches keep premultiplied values (as libjxl), so `JxlLayers` layers and
   `Flatten()` are unpremultiplied only at output. `ImageColorInfo.AlphaMode` keeps reporting `Premultiplied` for the
   stored samples (decision 4).

### Spot colours

5. New `Rendering/JxlSpotColors`: the spot channels (index, colour, opacity) of the image metadata, and
   `Apply(color, extra, …)` that mixes every spot channel in extra-channel order into the colour planes in row bands
   through `JxlParallel` (per-pixel, so identical at any thread count). A gray canvas (one plane, or the same plane three
   times) is mixed once with `spot_color[0]`. The arithmetic follows `SpotColorStage` without FMA (libjxl's scalar loop;
   GCC does not contract it at the flags libjxl uses, to be confirmed bit for bit against djxl).
6. Placement in `JxlDecodeSession`/`JxlFrameRenderer`, following libjxl's pipeline:
   - Frames that need no blending (still path, per-frame still path of animations, copied canvases, every
     `JxlLayers` layer): for XYB, inside `JxlColorOutput` between `XybToLinear` and the transfer function (a scalar
     row path used only when spot colours are present; with an ICC target the spot colour is mapped by the same
     linear-sRGB → profile matrix our conversion folds in, since libjxl mixes in linear sRGB before its CMS); for
     other frames right after the colour transform. These frames take neither the integer lossless path nor deferred
     YCbCr rows (as for noise and splines).
   - Blended canvases: after `Blend`, on the output copy of the canvas, before `JxlCanvasToSrgb` (`ToSrgb`); the slot
     keeps the canvas without ink.
   - When a frame is both stored as rendered (or blended) and displayed or sent to the layer sink without blending,
     the spot result and the plain result differ: the decoder keeps the XYB planes before the colour transform and
     renders the colour twice (once with spot colours). Only files with spot colours pay for it.
   - Frames stored before the colour transform and DC frames: no spot colours (libjxl's save stage comes first).
7. Spot rendering is always on, like djxl (decision 3); the spot channels are then dropped.

### Other types

8. No code change beyond the policy: they are decoded and dropped. Tests prove it for each type through every API.

### Limits and memory

- Premultiplied alpha: three float rows per worker in the float-plane path (as the integer path already rents),
  charged like the integer path's rows. Spot colours: no new memory except the second colour rendering of item 6
  (three float planes of the frame, charged to `JxlWorkBudget` through the frame's buffer scope). Extra channels are
  already charged (each channel is a plane of the frame, `K` unchanged). Cancellation per row band.

### Not in scope

- An API for extra channels (depth maps, selection masks) or for keeping premultiplied output: a possible later
  plugin-side idea, not part of 0.8.16.
- Writing premultiplied alpha or spot colours in the encoder.
- CMYK and float (see above).

## Tests and corpus

- Corpus tools (decision 2): `jxl_anim_gen` gets an `extra TYPE [key=value…]` directive (type alpha with
  `premultiplied`, spot with `color=r,g,b,a`, depth, selection, thermal, optional, unknown, black, bits, dim_shift,
  name) and per-frame patterns for every extra channel, so stills, layers and animations with any channel mix can be
  written through the libjxl encoder API; a small `jxl_dec_straight` (C++, libjxl decoder API with
  `JxlDecoderSetUnpremultiplyAlpha`, 8-bit or 16-bit RGBA PNG, coalesced frames or `--no_coalescing` layers) gives the
  straight-alpha oracle djxl cannot produce. Both in `tests/assets/tools`, built like `jxl_anim_gen`.
- New corpus files (`generate-corpus.py`): cjxl `--premultiply=1` lossless 8-bit, lossless 16-bit gray+alpha and lossy
  (VarDCT, alpha exact); jxl_anim_gen: premultiplied layers blended with Blend and AlphaWeightedAdd, a premultiplied
  animation, spot colour in a Modular RGB still, an XYB still (linear placement), a gray still, two spot channels with
  partial opacity, a spot channel with `dim_shift` (upsampled), spot colours on blended layers and an animation
  (output-space placement and slot without ink), alpha + spot, an image with Depth, SelectionMask, Thermal, Optional
  and Unknown channels (lossless and lossy), a second alpha channel, a 16-bit extra channel next to 8-bit colour; plus
  Black and float extra channel files as NotSupported cases.
- Oracle: every new file against djxl 0.12.0 (spot colours and dropped channels: djxl PNG; premultiplied:
  `jxl_dec_straight`), lossless exact, lossy within 1/255, alpha exact; also through the frame reader and `JxlLayers`
  (layers against `djxl --no_coalescing` / `jxl_dec_straight --no_coalescing`) and with `PreserveBitDepth` (16-bit
  references). Conformance: `spot` against djxl; `alpha_premultiplied` and `alpha_nonpremultiplied` against
  `jxl_dec_straight` (16-bit) and against `ref.png` unpremultiplied in the test within the conformance tolerance;
  `cmyk_layers` throws NotSupported with the new message.
- Unit: unpremultiply at alpha 0, 2^-26, tiny and 1, gray, `Rgba64`; spot mix with opacity 0 and 1, several channels in
  order, gray; messages of the Black/float rejections; 1 vs 16 threads identical; budget and cancellation in the new
  stages.
- Golden (`scripts/golden-hash.sh 0.8.15`, `JXL_GOLDEN_THREADS=1` and `16`): every existing result identical; only new
  files added.
- Fuzz (short): `decode`, `cancel-decode`, `diff-decode`, `frames`, `layers` with the new corpus as seeds.

## Deviations and results

- Spot placement, corrected while testing against libjxl: `PreparePipeline` also adds `FromLinear` before the stage
  that saves a frame for reference (`CanBeReferenced` and not `save_before_ct`), not only before blending. So linear
  mixing applies only to frames shown without blending that are not saved after the colour transform (the still path
  and the per-frame still path of animations, both through `JxlFrameDecoder.Finish`) and to every `JxlLayers` layer
  (no coalescing: neither stage exists). Every other displayed canvas gets the ink in output space on a copy
  (`JxlDecodeSession.WithSpotColors`) when the canvas is kept, in place otherwise. The double colour rendering of
  item 6 is therefore needed only for layers (`JxlSpotRendering.Copy`).
- `JxlColorOutput` cannot use the Rendering namespace (module rules), so the row mix is
  `JxlColorOutput.MixSpotRow`, used by both placements.
- Corpus: 26 new files from `jxl_anim_gen` (new directives `still`, `gray`, `alpha premultiplied`, `extra`,
  `ec_resampling`, frame `ramp=1`) and cjxl `--premultiply=1` (which only marks the alpha channel as associated, so
  colour can exceed alpha and stay above 0 at alpha 0: the amplification of decision 1). libjxl's encoder rejects the
  Unknown channel type, so it has no corpus file; the policy treats it like Depth. `dim_shift` cannot be set through
  the encoder API; `ec_resampling 2` covers upsampled extra channels.
- `jxl_dec_straight` links the GCC build of libjxl 0.12.0 (djxl is a static Clang build): identical to djxl on every
  lossless file, within 1/255 in a few samples on lossy files (checked on 16 corpus files before use).
- Results against the oracles: every new file matches (lossless exactly, lossy within 1/255; 16-bit output of the
  three 16-bit files exactly), coalesced, through the frame reader and as `JxlLayers` layers; conformance
  `alpha_premultiplied` and `alpha_nonpremultiplied` against `jxl_dec_straight`, `spot` against djxl;
  `cmyk_layers` throws with the CMYK message. Results are identical at 1 and 16 threads in every variant.
- Fuzzing: `diff-decode` compares premultiplied files with `jxl_dec_straight` (ToSrgb renderings of premultiplied XYB
  images outside sRGB are reported lenient, without an oracle). Seed 32, 5 min each: decode 1.85 M, cancel-decode
  518 k, frames 984 k, layers 1.84 M, no findings. Seed 33 diff-decode 179 k: one ToSrgb 2/255 mismatch on a mutated
  gray animation without extra channels (the pre-existing 0.8.15 kind), lenient/accept of the known container,
  metadata and colour kinds.
- Checks: Release build 0 warnings; tests 1316/1316 (23 skips: 8-bit files in the 16-bit oracle test, animations in
  the layer test); golden vs 0.8.15: 2159 results, 130 changed lines, only the 20 new files 0.8.15 rejected and the
  reworded CMYK/float messages, identical at 1 and 16 threads; pack 0.8.16 + consumer JIT and Native AOT (now reading
  `spot-premul.jxl`) pass. Speed: images without spot colours or premultiplied alpha take the 0.8.15 path (golden
  identical); no speed matrix rerun.

## Open decisions (user)

None open.

Decided (user, 2026-11-02): 1a (exactly libjxl's formula), 2a (`jxl_dec_straight` and the `extra` directive in
`jxl_anim_gen`), 3a (spot colours always rendered, no option), 4a (`Identify` keeps `Premultiplied`).

Options as proposed:

1. **Unpremultiplying where alpha is (almost) 0.** libjxl divides by `max(2^-26, alpha)`: exact premultiplied data
   (lossless) gives colour 0 at alpha 0, but a lossy file's small colour errors under transparent pixels become
   saturated colours (invisible, alpha is 0, but visible to code that ignores alpha).
   - (a, recommended) Exactly libjxl's formula: output identical to libjxl with unpremultiplying on, which keeps the
     AGENTS.md rule that decoder output matches libjxl.
   - (b) libjxl's formula, but colour 0 wherever alpha is exactly 0 after decoding: cleaner transparent pixels, a
     deliberate deviation from libjxl for those pixels only (alpha just above 0 still amplifies errors).
2. **Oracle for premultiplied files.** djxl 0.12.0 cannot unpremultiply.
   - (a, recommended) A small C++ dev tool `jxl_dec_straight` in `tests/assets/tools` against the existing libjxl 0.12.0
     build (decoder API with unpremultiplying on), plus the `extra` directive in `jxl_anim_gen`; neither is shipped,
     their outputs are committed.
   - (b) No new tool: unpremultiply djxl's 16-bit output in Python and compare within 1/255 (not exact, as libjxl
     unpremultiplies before dithering).
3. **Turning spot rendering off.** djxl renders spot colours unless `--norender_spotcolors`.
   - (a, recommended) Always on, no option: with the spot channels dropped, "off" would only lose the ink; an option
     makes sense together with a later extra-channel API.
   - (b) A plugin-side option now (for example a `JxlFormat` property), with an API snapshot change.
4. **`Identify` for premultiplied files.** Pixels are straight after decoding.
   - (a, recommended) Keep `ImageAlphaMode.Premultiplied`: `ImageColorInfo` describes the stored samples (core docs:
     "JPEG XL alpha_associated"), like `BitsPerSample` above 8 for 8-bit output.
   - (b) Report `Straight`, describing the decoded pixels.
