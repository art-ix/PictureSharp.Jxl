# Frame-by-frame reading for 0.8.13

Status: implemented (2026-11-02), not committed. Base: `1eb8958` (0.8.12).

PictureSharp 0.9.1 added an optional frame SPI for plugins (`IImageFormatModule.FrameDecoder`/`FrameEncoder`,
core docs/extending-picturesharp.md "Reading and writing frame by frame", core proposal
docs/proposals/plugin-frame-sequences.md section 4). 0.8.13 implements the reader. The roadmap moves by one (user
decision 2026-11-02): 0.8.14 animation encode with `FrameEncoder`, 0.8.15 noise and splines, 0.8.16 extra channels,
0.8.17 hardening, then 0.9.0.

Goal: `Image.OpenFrameReaderAsync` reads a JPEG XL file one displayed frame at a time: the frames, durations and loop
count `Image.Load` returns, with a working memory of a few canvases, so a long animation needs `MaxPixels` of one
canvas. `Image.Load`, `Identify`, layers and all existing results stay unchanged. Minimum PictureSharp becomes 0.9.1.

## Core contract (0.9.1)

- `OpenAsync(Stream, ImageFrameDecodeContext, CancellationToken)` returns an `ImageFrameSource` with
  `ImageFrameSequenceInfo` (size, `PixelType`, `FrameCount`, `LoopCount`, background). The stream is forward-only and
  already wrapped by the core so every byte read counts against `MaxInputBytes`.
- The core validates the canvas against `MaxPixels` (one canvas), the declared count against `MaxFrames` (1 with
  `FirstFrameOnly`), every frame's size, pixel type and ownership, and maps `EndOfStreamException`.
- `ColorConversion`, `TargetSize` and `ApplyExifOrientation` are rejected by the core before a reader opens, so the
  plugin never renders to sRGB and never flips the dither pattern.
- Metadata goes to `context.Metadata` with `ReserveMetadata`; there is no `ReservePixels`. No open-time token: each call
  carries its own.

## Design

1. **Input.** `OpenAsync` copies the stream into a `MemoryStream` (`CopyToAsync` with the token) and parses it as
   `Image.Load` does (`JxlContainer.Parse`, `jxlp` and `brob` unchanged). Compressed data is small next to the
   canvases, and the core bounds it with `MaxInputBytes`.
2. **Open.** Headers, the support policy and the ICC profile (`JxlDecodeSession.Open`, charged with
   `ReserveMetadata` unless `IgnoreMetadata`), then one header/TOC scan (`ReadFrameHeaders`, `MaxFrames`) gives
   `FrameCount` (displayed frames for animations, 1 otherwise) and the colour encoding of the first displayed frame
   (`JxlColorOutput.DescribeOutput`), so colour, EXIF, XMP and orientation are in `Metadata` before the first frame,
   applied in `Image.Load`'s order. `LoopCount` = `num_loops` when more than one frame is shown, else 0 (as
   `Image.Load`, also with `FirstFrameOnly`). Background: none (JPEG XL stores none).
3. **Resumable session.** `JxlDecodeSession.Run(callback)` becomes the iterator `Frames(animation)`, which yields
   `(header, JxlDecodedImage)` per displayed frame. Between yields the iterator keeps the reference slots, DC levels, the
   retained charge and the bit position of the next frame (`JxlBitReader` is a `ref struct`, so only its position is
   kept); a yielded image is valid until the next `MoveNext`, after which its frame buffers are returned, the budget is
   rewound and slots are stored, exactly as after the callback returned. `Decode` and `DecodeAnimation` are thin
   loops over it; `SkipRemaining` reads the remaining headers and TOCs for `FirstFrameOnly`. The token is a property set
   before each step; decoders built in a step read it then.
4. **Budget.** `JxlWorkBudget.Create(maxPixels)` returns the budget object; `Enter()` makes it current for one call
   and restores the previous value. `Begin` = create + enter, so `Image.Load` is unchanged. Retained slot canvases stay
   charged between calls because the object keeps `used`. Calls are synchronous inside `ReadNextAsync` (the data is in
   memory), so the `AsyncLocal` value is set and restored on the same thread and flows into `JxlParallel` workers.
5. **Output.** One `ImageFrame` of the canvas size and `PixelType`, allocated at the first frame, is overwritten by
   `JxlPixelWriter.WriteInto` for every frame (every writer sets every component, alpha 255/65535 without alpha).
   Durations as `Image.Load` (`JxlDecoder.Duration`; zero for stills).
6. **FirstFrameOnly.** The first displayed frame is returned; the next call runs `SkipRemaining` (MaxFrames, corrupt
   headers) unless that frame was last, then returns null, as `Image.Load` does.
7. **Disposal.** `DisposeAsync` disposes the iterator (its `finally` returns the current frame's buffers) and the
   decode-wide `JxlBufferScope` (DC and before-colour-transform slots), at any point; the checked build reports the
   budget then. Rentals are global counters, so a decode spanning calls needs no change to `JxlRentals`.

Memory: the source holds the compressed input, the reference slots (at most 4 + DC levels, float canvases as in
`Image.Load`), one frame's working buffers and the output frame. The working budget stays `K × MaxPixels + 64 MB`
(0.8.9) with `MaxPixels` of one canvas; files using all four slots at the full canvas need `K = 16` samples per pixel
already in `Image.Load`, so nothing new is rejected for corpus-sized inputs.

## Tests

- Every corpus file that `Image.Load` decodes: frames (pixels, durations), loop count, metadata and pixel type through
  the reader equal `Image.Load`, also with `PreserveBitDepth`, `IgnoreMetadata` and at 1 and N threads.
- A generated long animation (many frames) with `MaxPixels` = one canvas reads through the reader while `Image.Load`
  rejects it; `MaxFrames`, `MaxInputBytes`, `MaxMetadataBytes` limits; `FirstFrameOnly` (one frame, then null; MaxFrames
  still applies to the rest).
- Cancellation before open and between frames (pre-cancelled tokens), at any time from another thread; inside frames
  deterministically at every rental/charge in the checked build (`cancel-frames` fuzz target).
- Disposal after every frame count (sync and async), then a full read unchanged; outstanding rentals are checked by
  the counting pool of the fuzz build (`frames` disposes after a random frame); forward-only stream with short reads; truncated and corrupt input →
  `ImageFormatException`; unsupported → `NotSupportedException`.
- Fuzz: new `frames` (reader vs `Image.Load`, early disposal, rental check) and `cancel-frames` targets.

## Results

- Tests 900/900 (177 new in `JxlFrameReaderTests`); golden identical to 0.8.12 at 1 and 16 threads (1766 results).
- Fuzz, short runs: `frames` 1.37 M, `cancel-frames` 623 k, `decode` 1.41 M, `cancel-decode` 362 k; no findings.
- Pack + consumer JIT/Native AOT pass (reads `anim-ticks-loops.jxl` frame by frame with `MaxPixels` of one canvas).
- Deviation: with `FirstFrameOnly` a damaged later frame header fails at open (the frame count needs every header),
  not after the first frame; `Image.Load` rejects the same files.
