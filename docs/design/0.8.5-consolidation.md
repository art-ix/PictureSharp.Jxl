# Consolidation for 0.8.5

Status: released in 0.8.5. Base: `615ed07` (0.8.4).
Measurements: [speed.md](../benchmarks/speed.md#consolidation-085) and
[consolidation-0.8.5.json](../measurements/consolidation-0.8.5.json).

0.8.5 closes the improvement window (0.8.2–0.8.5) before memory work in 0.8.6 and fuzzing and resilience work from 0.8.7. Its scope from
the [SIMD roadmap](0.8.0-simd.md#roadmap-after-simd): small-image overhead, concurrency scaling and the benchmark
baseline the hardening releases compare against. Output is unchanged: decoded pixels and encoded bytes are identical to
0.8.4 (golden SHA-256 88eccd4b… for the 1433 earlier results, at 1 and 16 threads).

## Method

New speed inputs `small64` and `small256` (centre crops of the 12 MP photo, `scripts/make-speed-inputs.py`) with
`cjxl -d 0/1 -e 7` files give fixed per-image costs; `JXL_CONCURRENT=N` in the speed harness runs N copies of an
operation at once (`Parallel.For`), as a server handling independent images does. Profiles (dotnet-trace, CPU 0, one
thread) and allocation sampling (`GCAllocationTick` by type) of 0.8.4 chose the candidates. libjxl was timed with
`cjxl`/`djxl --num_threads=0 --num_reps=50` on CPU 0, which excludes process start-up.

0.8.4 against libjxl, one thread:

| Case | 0.8.4 | libjxl | Ratio | 1 MP photo ratio |
| --- | ---: | ---: | ---: | ---: |
| decode 64×64 lossless (e7) | 0.54 ms | 0.27 ms | 2.0× | 1.31× |
| decode 64×64 lossy (d1) | 0.20 ms | 0.20 ms | 1.0× | 1.41× |
| encode 64×64 lossless (e7) | 5.0 ms | 2.5 ms | 2.0× | 1.12× |
| encode 64×64 lossy (d1 e7) | 3.4 ms | 2.7 ms | 1.28× | 1.93× |
| encode 256×256 lossless (e7) | 94 ms | 45 ms | 2.1× | 1.12× |

| Profile (0.8.4, 1 thread) | Finding |
| --- | --- |
| encode 256×256 lossless e7 | RCT search 54%: 37 candidates × 3 channels, each over the whole image below 65536 pixels |
| encode 64×64 lossy | quantization tables recomputed per frame (19%); 7.0 MB allocated, 4.7 MB of it coefficient orders for DCT256 |
| decode 64×64 lossless | the ICC target (sRGB tone curve from 4097 `Math.Pow` calls) built for every image, used by none of them |
| 16 concurrent lossy encodes, 256×256 | default parallelism allocated 13.2 MB per image (4.1 MB at one thread): one worker state per potential worker |

## Changes

| Change | Effect (1 thread unless noted) |
| --- | --- |
| RCT search costs each distinct transformed channel once (12 shared channels plus 18 YCoCg ones instead of 111); candidate costs sum the channel costs in the old order, so the choice is identical | lossless e7 encode 64×64 −50%, 256×256 −42%, 1 MP −7.4% (final matrix) |
| Library quantization tables (`JxlQuantWeights`) are computed once per process and shared read-only; tables a frame signals stay per instance | lossy decode 64×64 −23%, 256×256 −9%; 0.5 MB less per lossy encode |
| Coefficient orders cover only the buckets up to the largest one the frame uses (the encoder never uses DCT128/256) | lossy encode 64×64 −20%, 7.0 → 2.3 MB, no gen-2 collections |
| The decoder's ICC output target is parsed on first use (only images whose colour encoding is an ICC profile render to it) | lossless decode 64×64 −36% |
| `JxlParallel.ForWorkers` creates a worker's state with its first item | 16 concurrent 256×256 lossy encodes at -1: 5.9 → 5.1 ms per image, 13.2 → 5.8 MB |

## Concurrency scaling

With tiered compilation off, independent images decoded or encoded 16 at a time on 16 logical CPUs reach the same
throughput with the library's default parallelism (-1) as with one thread per image, except where per-worker scratch
was created for idle workers (fixed above). An image's own region runs on the thread pool next to
the callers' work, and the pool's work-stealing absorbs it.

With tiered compilation on (the .NET default), a harness that warms up for 50 calls times small images partly in tier-0
code: 256×256 lossy decode 4.3 ms against 1.3 ms with tiering off. A server reaches tier 1 after the first calls; the
measurements keep tiering off as before.

## Not done

| Candidate | Reason |
| --- | --- |
| ReadyToRun code in the package (first call: 70–110 ms decode, 110–200 ms encode at 64×64, JIT) | RID-specific code and a larger package; a packaging decision for the user |
| 16-bit lossless decode ≤ 1.1× the 8-bit time (decision 6) | still about 1.45×: `cjxl` trees for real 16-bit content are 5–10× larger; tree descent, not a consolidation item |
| Lossy encode at libjxl's speed (1.9× `cjxl` from 64×64 to 1 MP) | encoder search work, outside this release |
| Tree learning scratch (`Search.Reuse` clears per node) for small lossless encodes | 9% of a 256×256 encode, interleaved with the learner's search order |

## Baseline for hardening

The final matrix (`artifacts/perf-0.8.5/final-paired.json`, summarized in the measurements file) and the golden results
including the small inputs (`artifacts/golden/0.8.5/golden-all-efforts.txt`, 1469 results) are the reference that
0.8.6–0.9.0 compare against: memory and hardening changes must keep the golden results and report speed against this matrix.
