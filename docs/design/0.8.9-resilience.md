# Resource budgets, failure paths and encoder fuzzing for 0.8.9

Status: prepared for release as 0.8.9 (2026-10-31). Base: `af78924` (0.8.8). The overflow audit and the `limits`
target moved to 0.8.10 (user decision 2026-10-31, release without them).

0.8.9 is the third step of the fuzzing and resilience series (roadmap in plan.md: 0.8.7 mutation fuzzing, 0.8.8
differential interoperability, 0.8.9 resource budgets, failure paths and encoder fuzzing, 0.8.10 long campaigns,
0.9.0 stabilization). 0.8.7 checked that every input decodes or fails cleanly, and 0.8.8 that the result agrees with
libjxl. 0.8.9 checks what a decode, encode or transcode costs and how it ends when it is stopped: memory and time
bounded by the declared limits, cancellation honoured promptly, every rental returned on every exit, and failing
streams reported unchanged. It also adds the encoder targets moved from 0.8.7. Decoded output and encoded bytes do
not change unless a finding needs it: golden stays identical to 0.8.8 (1524 results) at 1 and 16 threads.

## What exists

- Limits: the decoder charges the output canvas (`ReservePixels`, Rgba64 twice) and every metadata byte
  (`ReserveMetadata`, ICC before decompression, brob incrementally); `JxlTranscoderOptions` has `MaxPixels`,
  `MaxInputBytes` and `MaxMetadataBytes`; the global MA tree is capped at `min(2^22, 1024 + pixels·channels/16)` nodes;
  counts read from the bitstream are checked against the remaining input (`JxlBitReader.EnsureRemaining`).
- Point tests: `Decode_ChecksThePixelLimitAndCancellation`, `Limits_MetadataIsChargedBeforeItIsMaterialized`,
  `Budget_ChargesSixteenBitPixelsTwice`, `Budgets_FailBeforeWorkersAtEveryDegree`,
  `Cancellation_DuringAParallelDecodeOrEncode_Throws`, `SymbolWindow_IsReturnedOnce_OnSuccessCorruptionAndCancellation`,
  `BufferScope_AcceptsConcurrentRentalsAndReturnsEachOnce`, `StreamingOutput_IsExactAndSurvivesFailure`,
  `StreamValidationAndIoFailures_PropagateWithoutClosingStreams`, `HugeDimensions_AreLimited`.
- The 0.8.7/0.8.8 harness: supervisor and workers, reproducible inputs from `(seed, iteration)`, heap limit
  (`--heap-mb`, default 2 GiB), time limit, `JXL_FUZZ_CHECKED`, `scripts/fuzz.sh`.

What is missing: these tests stop at one chosen point (one cancellation, one failing write, one limit). Nothing
cancels at every point of a run, fails a stream at every byte, counts rentals across a whole run, or bounds the
working memory that the output charge does not cover. The encoder has no fuzz target.

## Working memory

The core documents `MaxPixels` as a bound on the pixel storage of the returned image, "not all working memory". The
JPEG XL decoder needs far more than the output: in 0.8.6 a 12 MP recompressed JPEG used ~0.9 GB RSS for a 48 MB
canvas. That is normal; what matters is that the working memory stays proportional to what was charged, so that a
small file cannot make a large allocation pass the limits.

From reading the code (to be confirmed by the `limits` target below, before any fix):

- **Extra channels.** The image header may declare up to 4096 extra channels (`JxlImageMetadataReader`; each takes at
  least one bit, so a few hundred bytes suffice). Channels of unknown type (depth, selection mask, optional, ...) pass
  `EnsureImageSupported` and are decoded and dropped, but `JxlFrameDecoder` creates a full-size 32-bit `JxlChannel`
  for each: 4096 channels of a 4096×4096 image are 256 GiB of `int` storage, of which only the 64 MiB canvas is
  charged. The allocation is lazy (first row access), so a heap-limited run would show it as `OutOfMemoryException`.
- **Non-displayed frames.** Reference frames (up to 4 slots), DC frames (up to 4 levels) and patch sources are kept
  at full size alongside the image. Their count per slot is bounded, their total is not charged.
- **Modular transforms.** Palette and squeeze add or resize channels; the number of transforms and squeeze steps is
  bounded only by the input size.
- **Frame count.** Reference-only frames saved after the colour transform are skipped without decoding, so a file may
  hold any number of them; each costs a header and TOC read, not their pixels. `MaxFrames` is not applied to
  non-displayed frames.

Decided (user, 2026-10-31): a per-decode working budget, internal, with no new API.

- `JxlWorkBudget`, owned by the decode session (and by `JxlTranscoding`), charged on the calling thread before a
  plane, channel, reference frame or token buffer is allocated, like the 0.8.1 rule for budgets ("charged on the
  calling thread"). Parallel workers charge nothing: their scratch is sized by the region and charged once before it
  starts.
- Limit: `K × MaxPixels` 32-bit samples. K comes from the 0.8.6 memory matrix: the largest charged working set per
  output pixel over the corpus and the speed matrix, plus a margin, recorded here once measured. The 12 MP decode's
  ~75 bytes of RSS per pixel (pool retention and GC included) puts the first estimate at K = 16 (64 bytes per allowed
  pixel: 4 GiB at a 64 MP `MaxPixels`, 16 GiB at the default 2^28). At the default the budget is a backstop against
  files that ask for orders of magnitude more (the extra-channel case above asks for 4096 samples per pixel), not a
  tight bound; a caller who lowers `MaxPixels` lowers it too. Exceeding it is `ImageFormatException`
  ("JPEG XL decode needs more working memory than MaxPixels allows"), not `NotSupportedException`: it is a limit
  like `MaxPixels`, raised the same way.
- Extra channels that are not alpha are still decoded (the bitstream interleaves them) but their storage is charged.
  Dropping their samples while decoding would save the memory but changes the Modular decode order; not proposed.
- `MaxFrames` counts every frame read, displayed or not; the core already applies it to `Identify`.
- Pixels are unchanged; golden cannot move.

Alternatives: a public option such as `JxlDecoderOptions.MaxWorkingBytes` through `DecoderOptions.FormatOptions`
(more control, new API and snapshot); or fixed caps like libjxl's fuzzer build (e.g. at most 256 extra channels),
which reject valid files.

The encoder has no input limit to derive a budget from (the caller owns the image). Its working memory is measured
by the encode target below and recorded (peak managed bytes per input pixel per effort), not limited.

## Overflow

- Audit every size product in src (`width * height`, `* channels`, group and TOC offsets, `Array.MaxLength` checks,
  `checked(` sites: 54 in 16 files) for `int` overflow before the check. Each site gets either a `long` product with
  an explicit limit or a comment saying why the operands are already bounded.
- `limits` target (new): headers and frame headers built from a parameter blob with dimensions up to 2^30, 1–4096
  extra channels, every upsampling factor, group dimensions, DC levels and reference slots, run with `MaxPixels` and
  `MaxMetadataBytes` at `long.MaxValue` and under the 2 GiB heap limit. Pass: decodes, or the usual exceptions; an
  `OutOfMemoryException`, `OverflowException`, `IndexOutOfRangeException` or a run over the time limit is a finding.
  The same blob with the default limits must fail in the header or budget check, before any large allocation
  (checked by the rental counter below: no rental above 1 MiB before the throw).

## Cancellation

- `cancel` mode for the `decode`, `tojpeg`, `fromjpeg` and new `encode` targets: each input runs once to measure its
  duration, then again with `CancelAfter` at a fraction drawn from the seed (0–100%), at 1 and 4 threads. Pass: the
  result of the full run, or `OperationCanceledException` with that token. Any other exception, a result that differs
  from the full run, or a leaked rental is a finding.
- Latency: from the cancellation to the throw, at most 50 ms on the PC for every corpus file and the 12 MP speed
  matrix images (decode, lossy e7 and lossless e7 encode, both transcoder directions). The current checks are every
  `CancellationCheckMask + 1` pixels in the encoder, per row or group elsewhere; the long ones are found by timing,
  not guessed.
- Async overloads (`FromJpegAsync`, `ToJpegAsync`, `SaveAsJxlAsync`): a token cancelled before the call and during the
  stream copy.

## Pooled buffers

- The checked build (`JXL_FUZZ_CHECKED`) routes every rental through a counting pool: `JxlPooledBuffer`,
  `JxlBufferScope`, and the direct `ArrayPool<T>.Shared` sites (`JxlTokens`, `JxlMaTree`, `JxlSymbolReader`). It counts
  rentals and returns per operation and records the largest one. Every target asserts after each run, success or
  failure, that the counts are equal, and that no array was returned twice. The release build keeps
  `ArrayPool<T>.Shared` directly (`#if` only, as for the `Unsafe.Add` checks of 0.8.7).
- The stale-data check of 0.8.7 (second run on returned buffers) stays.
- `JxlColorRows`, `JxlDecodedImage`, `JxlReferenceFrame` and the encoder's scratch are audited for buffers that
  outlive their scope on an exception path (for example a buffer rented before a `try`).

## Failed streams

- Output: a stream that throws `IOException` after N bytes, or once at every N, for `Save`/`SaveAsJxl`, `FromJpeg`
  and `ToJpeg`, sync and async, N drawn from the output length. Pass: the `IOException` itself (not wrapped), the
  stream left open, no leaked rental, and the next operation on a new stream byte-identical to an undisturbed one.
- Input (transcoder streams): short reads of 1 to N bytes, a read that throws, a stream that reports a wrong `Length`,
  a non-seekable stream, and inputs exactly at and one byte above `MaxInputBytes`.
- Documented: what is left in the output stream after a failure (bytes already written; nothing is rolled back).

## Encoder fuzzing

New targets, moved from 0.8.7 (user decision 2026-10-30):

| Target | Entry | Input |
| --- | --- | --- |
| `encode` | `Image.Encode` with `JxlEncoderOptions`, then `Image.Load` | parameter blob: width and height 1–2048 (log-skewed, every boundary width of the 0.8.7 set), Rgba32 or Rgba64, alpha (none, opaque, binary, varying, all transparent), gray or colour, content (noise, gradient, flat, few colours, crops of corpus images), quality or distance 0–25, effort 1–9, `CompressMetadata`, ICC/EXIF/XMP blobs (valid and random) |
| `edit` | `Image.EditMetadata` on a corpus file with ICC/EXIF/XMP from the blob, then decode | corpus `*.jxl` + parameter blob |

Checks:

- lossless (distance 0): the decode returns the source exactly, at the source's bit depth;
- lossy: the decode has the source's size and bit depth, alpha is exact, and ssimulacra2 is not compared here (that is
  `diff-encode`); a decode that fails is a finding;
- the bytes are identical at 1 and 4 threads and on a repeated encode (pooled buffers reused);
- metadata: ICC, EXIF and XMP come back byte for byte; `edit` leaves the decoded pixels identical to the original's;
- the rental counter, cancellation and failing streams as above;
- peak managed allocation per input pixel recorded per effort (no limit, see Working memory).

`diff-encode` (0.8.8) keeps the comparison with djxl; `encode` runs without libjxl and therefore also under AFL++,
where the blob is the fuzzed input. At ~75 inputs/s for `diff-encode`, `encode` sizes are capped at 2048×2048 and
effort 8–9 at 256×256.

## Harness

- `tools/PictureSharp.Jxl.FuzzTargets`: `limits`, `encode`, `edit`; `cancel` and `stream` modes as flags applying to
  the existing targets (`--mode cancel|stream`), so signatures stay per target.
- `tools/PictureSharp.Jxl.Fuzz`: generators for the parameter blobs; `repro` prints the rental counts and the largest
  rental.
- `scripts/fuzz.sh resilience [--time SEC] [--workers N]`: the new targets and modes in parallel, output in
  `artifacts/fuzz-0.8.9`; `status` and `repro` as before.
- Finding kinds: the 0.8.7/0.8.8 kinds plus `leak` (unequal rental counts), `budget` (allocation over the working
  budget, or a large rental before a limit check), `latency` (cancellation slower than the limit).

## Machines

Campaigns on the x86 PC: 10 minutes per target and mode, 3 workers, seeds 1–3, as in 0.8.8 (decision 2). The Orange
Pi stays for the 0.8.10 long campaigns, unless it is available again (decision 3).

## Findings

Each finding gets a minimized input in `tests/assets/corpus/fuzz/` (or a parameter blob in
`tests/assets/corpus/resilience/`) and a regression test that runs it through the same pass rules without the
fuzzer. The working budget gets its own tests: a synthetic file declaring many extra channels is rejected at the
default limits and decodes with a raised `MaxPixels`; the budget fails before workers start at every degree.

## Done when

- every new target and mode has run its PC campaign with no open finding;
- the working budget is measured against the 0.8.6 memory matrix, its factor recorded, and no corpus or speed-matrix
  file is rejected at the default limits;
- the overflow audit lists every size product in src (moved to 0.8.10);
- cancellation latency is within the limit for the corpus and the 12 MP matrix;
- tests and golden (1524 results, unchanged) pass at 1/-1 threads, the package and the JIT/AOT consumers pass, and the
  release build shows no time regression (targeted check on the 1 MP and 12 MP decode and e7 encode).

## Results

### Working budget (done 2026-10-31)

Confirmed before the fix with files written by the internal encoder (gray, N extra channels of type Optional, all
samples zero, e1), all decoded by djxl v0.12.0:

| File | Size | Charged canvas | Allocated by 0.8.8 | djxl RSS |
| --- | ---: | ---: | ---: | ---: |
| 256x256, 64 channels | 269 B | 256 KiB | 17 MiB | |
| 1024x1024, 64 channels | 374 B | 4 MiB | 282 MiB | 106 MiB |
| 2048x2048, 256 channels | 1369 B | 16 MiB | `OutOfMemoryException` under a 2 GiB heap | |

Implementation: `Codestream/Buffers/JxlWorkBudget.cs`. The budget is ambient for the operation (`AsyncLocal`, which
`Parallel.For` carries into the workers), started by `JxlDecoder.Decode` and `JxlTranscoding.ToJpeg`, and charged
by `JxlPooledBuffer` (every rental), `JxlChannel` and `JxlPlane` (allocations outside a scope). It counts every
charge, released or not, so the result does not depend on the thread count or the GC. `FromJpeg` is bounded by
`MaxPixels` on the JPEG and the encoder by the caller's image; neither has a budget.

Measured K (charged bytes / 4 / output pixels, every corpus file, speed input and private sample, default options
and PreserveBitDepth + ToSrgb at all threads): at most 8.99 for images of at least 64K pixels (12 MP 16-bit lossless
8.98, 12 MP 8-bit lossless 7.0, lossy 6.6–6.8). Small images are dominated by fixed costs (block padding, group
scratch): at most 3.7 MB beyond 64 bytes per pixel (`lf-groups.jxl`, 1100x40). Hence:

- `SamplesPerPixel` K = 16 (1.78x the largest measured), plus `FixedBytes` = 64 MiB;
- limit = 64 MiB + 64 bytes × `MaxPixels`: 320 MiB at the fuzzers' 2^22, 16 GiB at the default 2^28;
- `MaxFrames` now counts every frame read (reference, DC and skipped frames too).

At the default `MaxPixels` the budget is a backstop: the 2048x2048 file above needs ~4.3 GiB and passes it (as it
passes in libjxl). A caller who lowers `MaxPixels` to what they accept gets a budget of the same order.

Tests: `JxlResilienceTests` (both files rejected with "working memory" at a `MaxPixels` equal to their size or 2^22,
at 1 and 4 threads, before their storage is allocated; corpus images decode at a `MaxPixels` of exactly their size;
`MaxFrames` = 1 rejects `lossy-patches.jxl`). Inputs in `tests/assets/corpus/resilience/`.

Checks: tests 546/546; golden 1542 = 1524 identical to 0.8.8 + 18 for corpus/resilience, the same lines as the 0.8.8
package gives, at 1 and -1 threads. Decode time against the 0.8.8 package (best of 5, two alternating rounds; 1 MP and
12 MP, lossy d1 and lossless e7, 1 and all threads): 0.89–1.02x, noise.

### Pooled buffers (done 2026-10-31)

- `Codestream/Numerics/JxlArrayPool.cs`: every rental in src goes through `JxlArrayPool<T>.Shared`
  (`JxlPooledBuffer`, `JxlSymbolReader`'s LZ77 window, `JxlMaTree`, `JxlTokens`). In the release build it is
  `ArrayPool<T>.Shared` (`ReleaseBuild_RentsFromTheSharedPool`); under `JXL_FUZZ_CHECKED` it is a counting pool that
  tracks live arrays by reference (`ConditionalWeakTable`), the outstanding count and the largest rental, and records
  an array returned twice or never rented. Empty arrays are not counted (`Rent(0)` hands out the shared empty
  array). It sits in Numerics, which every module may use (`ModuleBoundaryTests`: Entropy may depend on IO only).
- `FuzzTargets.Run` resets the counters before each input and checks them on success and after an allowed
  exception; a difference is a `leak` finding (`FuzzLeakException`, "After <exit>: N rentals not returned
  (<type>[<length>], ...)"), whose signature is the exit and the element types. `repro` prints the largest rental.
- Detection checked by removing the return of the LZ77 window: `effort1.jxl` is reported as
  "After success: 2 rentals not returned (UInt32[1048576])".
- Results: every corpus file through `container`, `headers`, `decode`, `tojpeg` and `fromjpeg`, then 5 minutes per
  target, all six in parallel, 2 workers, seed 9 (decode 1.53 M, fromjpeg 0.51 M, entropy 13.1 M, tojpeg 15.3 M,
  headers 53 M, container 81 M inputs): no leak, no other finding.
- Checks: tests 547/547; golden 1542 identical to 0.8.8 at 1 thread (the release build rents as before).
- Still to come: the audit of buffers that outlive their scope on exception paths runs with the cancel and stream
  modes, which reach exits the mutated inputs do not (a cancellation between a rental and its `try`).

### Cancellation and failing streams (done 2026-10-31)

Implemented as six targets in `tools/PictureSharp.Jxl.FuzzTargets/ResilienceTargets.cs` rather than a `--mode` flag:
they take the seeds of the target they wrap (`stream-encode` those of `decode`), so the harness needed no new option.

- Deterministic cancellation instead of `CancelAfter`: the checked build counts every rental and working-budget
  charge (`JxlRentals.Event`, `OnEvent`). `cancel-decode`, `cancel-tojpeg` and `cancel-fromjpeg` run an input once,
  then cancel at four events drawn from its hash, each at 1 and 4 threads. Pass: `OperationCanceledException` with
  that token or the uncancelled result, and the pool balanced after every run. A point is reproducible at one thread
  and lands between a rental and the next check, the case the design worried about. `JXL_FUZZ_CANCEL_ALL=1` tries
  every event at one thread (corpus sweeps), `JXL_FUZZ_VERBOSE=1` prints each point and its outcome.
- `stream-tojpeg`, `stream-fromjpeg`: the same output from a non-seekable stream returning 1–7 bytes per read; a read
  failing at byte n and a write failing after n bytes, sync and async, must end with that `IOException` (same
  instance, not wrapped), both streams open, and the bytes written a prefix of the full output.
- `stream-encode`: a decoded seed encoded (lossless or distance 1–4, effort 1–3) into a stream failing after n
  bytes, with the same checks; an encode that fails at all is a mismatch.

Results:

- Corpus sweep of every event at one thread: decode 19 793 points, `ToJpeg` 4 171, `FromJpeg` 4 111; all cancelled
  cleanly or returned the full result, no leak.
- PC campaign 5 min per target, 2 workers, seed 10: cancel-decode 0.35 M, cancel-tojpeg 6.3 M, cancel-fromjpeg
  0.26 M, stream-tojpeg 10.8 M, stream-fromjpeg 0.28 M inputs; no finding. (The first `stream-encode` run tested
  nothing: without `Configuration` on the encoder options every save was an allowed `NotSupportedException`; fixed,
  see below.)
- `stream-encode`, 5 min with 4 workers, seed 11: one `mismatch` (12 inputs), a mutated `icc-profile.jxl` whose ICC
  profile has a damaged colour space signature. djxl decodes it and hands the profile on unchanged
  (`--orig_icc_out`), as this library does, but the encoder cannot describe such a profile and refuses it. Not a
  defect: the target now encodes again without the profile and counts only a failure there. Rerun after that fix,
  2 workers, seed 12: 1.97 M inputs, no finding.
- `fuzz.sh` reuses the fuzzer it published into `--out`/build: after changing the targets, remove that folder (the
  first run of these targets failed with "Unknown target").

run, time from `Cancel()` to the exception, PC:

Fixed (output unchanged): the encoder had two stretches without a check. `ChromacityAdjustments` makes two scalar

`WriteStream`, which take one: the histograms of all tokens ran unchecked (129 ms at 16 threads). The remaining
worst case, 35 ms at 95% of a lossy encode, is the value histograms of the AC tokens, which check per stream.
Every case is within the proposed 50 ms.

Checks: tests 547/547; golden 1542 identical to 0.8.8 at 1 and -1 threads after the encoder fixes.

### Encoder fuzzing (done 2026-10-31)

`tools/PictureSharp.Jxl.FuzzTargets/EncodeTargets.cs`: the `encode` and `edit` targets as designed above, with these
details:

- `encode` blob: the `diff-encode` layout (flags, effort, distance, size) plus byte 7 (size shift 0–3 so most
  images are small, alpha kind: opaque, binary, as generated, fully transparent; `CompressMetadata`; EXIF; XMP;
  random metadata bytes) and byte 8 (quality instead of distance). Sides up to 2048 (256 for efforts 8 and 9).
  Seeds: 256 generated blobs, one per flag combination. The ICC profile is that of `icc-profile.jxl` (not under
  AFL++, where the ICC flag does nothing).
- Rules learned from the first runs (none a defect): random EXIF may come back absent, since the decoder skips EXIF
  that is not a TIFF stream; random metadata the encoder refuses must encode without it; lossy frames may store a
  describable ICC profile as an enumerated encoding, so the profile is compared for lossless frames only.
- `edit`: recompressed JPEGs (`jbrd`) must refuse every edit (`NotSupportedException`, docs/metadata.md); a file
  whose EXIF PictureSharp cannot parse is refused by the core before the plugin is called
  (`ImageMetadataService.Rewrite`, "Malformed EXIF", for every format), which the target accepts. Two such inputs
  from the first campaign (mutated EXIF boxes) are kept in `artifacts/fuzz-0.8.9/custom/edit-seed13`.
- Results: the 256 `encode` seeds and the corpus through `edit` pass. PC campaign 5 min each, 3 workers, seed 13:
  `encode` 6 898 inputs (large images, three encodes and a decode each), no finding; `edit` 2.93 M inputs, the two
  core refusals above. `edit` again after the rule, seed 14, 2 min: 1.46 M inputs, no finding.
- Not done: the peak managed allocation per input pixel per effort (a measurement for the docs); moved to 0.8.10
  with the longer encoder campaigns.
- `tools/PictureSharp.Jxl.SharpFuzz` lists the new targets (`encode`, `edit`, `cancel-*`, `stream-*`).
