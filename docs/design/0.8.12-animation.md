# Animation decoding for 0.8.12

Status: implemented (2026-11-02), not committed. Base: `2409ebb` (0.8.11).

0.8.12 is the third step of the feature series (roadmap in plan.md: 0.8.10 blending and flattened layers, 0.8.11
plugin layer API, 0.8.12 animation decode, 0.8.13 animation encode, 0.8.14 noise and splines, 0.8.15 extra channels,
0.8.16 hardening, 0.9.0). 0.8.10 made the decoder blend frames onto canvases kept in reference slots; an animation
frame is exactly such a canvas, shown for a while.

Goal: `Image.Load` decodes a JPEG XL animation into a multi-frame `Image` whose frames are the frames `djxl` shows with
its default coalescing, with their durations and the loop count, within the existing limits, cancellation and thread
rules. `Image.Identify` reports the frame count. No public API change. Still images and every existing result stay
unchanged.

## What exists

- `Frames/JxlDecodeSupportPolicy.EnsureImageSupported` throws `NotSupportedException("animations are not decoded
  yet.")` when the image header has an `Animation` block; `JxlImageInfoMapper` reports `IsAnimated = true` and
  `FrameCount = null` for such files without reading frames.
- `JxlAnimationHeader(TicksNumerator, TicksDenominator, Loops, HaveTimecodes)` is parsed; `JxlFrameHeaderReader`
  reads each frame's `Duration` and skips the timecode; `Name` is read. `ReadSaveBeforeColorTransform` already uses
  libjxl's `CanBeReferenced` rule to decide whether the field is present.
- `Frames/JxlDecodeSession.Decode` (0.8.10) loops over frames: DC and before-colour-transform frames go to
  `JxlReferenceFrames`; other frames are rendered in the original encoding with their own `JxlBufferScope`, blended or
  copied into a GC-owned canvas, stored in slot `SaveAsReference` when not last, and `JxlWorkBudget.Rewind` keeps only
  the charge of retained canvases. The last frame is returned as a `JxlDecodedImage`; when it needs no blending it takes
  the still-image path (`JxlFrameDecoder.Finish`: integer samples, deferred YCbCr rows). Every non-last frame is
  stored, which is right for stills (all their frames have duration 0) but not for animations.
- `JxlDecodeSession.ReadFrameHeaders` reads every frame header and TOC without decoding sections (used by
  `JxlLayers`); `maxFrames` limits all frames stored in the codestream, displayed or not (0.8.9).
- `Integration/JxlDecoder.Decode` reserves one canvas, runs the session, writes it with `JxlPixelWriter.Write`/
  `WriteWide` (dither flipped for the orientation, `DitherFlip`) and applies colour, metadata and orientation.
- `JxlLayers.Load` rejects animations (`JxlLayerStack`: "animations have frames, not layers").
- Corpus: `animation.jxl` (3-frame 16×16 RGBA APNG, lossless) is in `JxlDecodeTests.Unsupported` and expected to
  throw; golden records the exception.

Core facts (PictureSharp 0.9.0, docs/animation.md):

- An `Image` holds `Frames`; every frame is a full canvas of the image size with its own `Duration` (`TimeSpan`);
  `Image.LoopCount` counts plays, 0 = forever. A plugin appends a frame with `Frames.Add(ImageFrame)` (public
  `ImageFrame(width, height[, pixelType])`, `GetPixelMemory<T>()`, `Duration`); `HasAlpha` follows the frames.
- `ImageDecodeContext.ReservePixels(w, h, type, frames)` accumulates over the load: `MaxPixels` sums all frames
  (Rgba64 twice) and `MaxFrames` sums the reserved frames. `DecoderOptions.MaxFrames` is documented as the limit of
  frames stored in the file, also with `FirstFrameOnly` and in `Identify`.
- With `FirstFrameOnly` the core decoders return one frame; PNG and GIF then report `LoopCount = 0` (PNG:
  `animated ? NumPlays : 0`, GIF: `frames.Count > 1 ? … : 0`), WebP keeps the container's loop count.
- After the decoder returns, the core converts colour, applies `TargetSize` and `ApplyExifOrientation` to every frame.
- `Image.OpenFrameReaderAsync` covers GIF, PNG and WebP only; there is no SPI for a plugin frame reader.

## What libjxl does (v0.12.0)

- Coalescing (decode.cc, `JxlDecoderProcessInput`): with coalescing on (the default, as djxl uses it) a frame is shown
  when `is_last_of_still = is_last || animation_frame.duration > 0`. Reference-only and DC frames have no duration and
  are never shown. A regular frame with duration 0 that is not last is an internal frame: it is decoded, blended and
  saved to its slot, but not returned; the next shown frame blends onto that slot. There is no extra merging step:
  the frame headers already say how frames compose.
- `CanBeReferenced` (frame_header.h): not last, not a DC frame, and `duration == 0 || save_as_reference != 0`. A
  shown frame with duration > 0 and `save_as_reference == 0` is not saved; slot 0 keeps its previous content.
- `JxlDecoderGetFrameHeader` reports the shown frame's own `duration` in ticks (and the timecode when present);
  with coalescing it reports the full canvas size, no crop and Replace. Frame names are reported, but djxl's image
  outputs do not keep them.
- Basic info: `animation.tps_numerator/tps_denominator` (ticks per second), `num_loops` (0 = forever),
  `have_timecodes`. djxl writes APNG with `num_plays = num_loops` and each delay as the fraction `duration × tps_den / tps_num`
  seconds (enc/apng.cc).
- cjxl: APNG input gets ticks 1000/1 and millisecond durations; frames are cropped to their fcTL rectangle, blend from
  slot 1 (Blend for `APNG_BLEND_OP_OVER`, else Replace) and are saved to slot 1; dispose ops insert placeholder frames
  of duration 0 (apng.cc). GIF input gets ticks 100/1. cjxl never sets `num_loops` (always 0) or timecodes.

## Design

### Decode loop

`JxlDecodeSession` gets a display sink and a stop condition; the still path (`metadata.Animation is null`) keeps
today's `Decode()` unchanged and is the acceptance gate for golden.

For an animation the loop is the 0.8.10 loop with three changes:

1. Displayed = regular or skip-progressive and (`IsLast` or `Duration > 0`). Each displayed frame goes to the sink as
   a `JxlDecodedImage` of the canvas size together with its duration; the sink returns false to stop (FirstFrameOnly).
2. Saving follows `CanBeReferenced`: a frame is stored in slot `SaveAsReference` only when not last and
   (`Duration == 0` or `SaveAsReference != 0`). The same rule is applied to stills (no change there: their non-last
   frames all have duration 0).
3. A displayed frame that needs no blending (full size, Replace for colour and every extra channel) and is not
   referenceable takes the still path per frame: its own `JxlBufferScope`, `JxlFrameDecoder.Finish` (integer samples,
   deferred YCbCr rows), written by the sink before the scope is disposed. Every other displayed frame is rendered,
   blended or copied into a canvas as in 0.8.10, stored if referenceable, and passed to the sink as the canvas.

Frames stay sequential (each may depend on the slots of the previous ones); groups, rendering and blending inside a
frame stay parallel as today, so results are identical at 1 and N threads.

### Output

- `JxlDecoder` keeps one code path: the first displayed frame becomes the `Image` exactly as a still does (same writer,
  same dither flip); each later frame is written into a new `ImageFrame` of the image's pixel type through the same row
  writers (they target `GetPixelMemory<T>()` of a frame instead of an `Image`) and appended with `Frames.Add`.
- `ReservePixels(width, height, pixelType, 1)` is called before each frame's pixels are allocated (the first one as
  today), so `MaxPixels` and `MaxFrames` fail before allocation and count only what is produced.
- `Duration` = ticks × tps_den / tps_num seconds as a `TimeSpan`, computed in 128-bit integers and rounded to the
  nearest 100 ns tick (exact for every ticks rate whose tick is a multiple of 100 ns, e.g. 1000/1 and 100/1);
  saturates at `TimeSpan.MaxValue` (only reachable with absurd headers). Duration 0 on the last frame stays 0, like
  the core's GIF decoder.
- `LoopCount = num_loops`, clamped to `int.MaxValue` (the core property is an `int`); see decision 3 for single-frame
  results.
- Timecodes and frame names are dropped (the core has no fields for them; plan.md).
- Metadata (colour description, EXIF, XMP, orientation) is applied once to the image, as for stills. All frames share
  one colour description: the fast and canvas paths both produce the original encoding, or sRGB with
  `ColorConversion = ToSrgb` for XYB (fast path renders to sRGB, canvas path converts the blended canvas, as 0.8.10
  does for blended stills). The decoder asserts that every frame has the description of the first one (an internal
  invariant, `InvalidOperationException` in tests if broken).
- Orientation: as for stills; the dither pattern is flipped per frame when `ApplyExifOrientation` is set, and the core
  orients every frame afterwards.
- A failure or cancellation after some frames disposes the partial image before the exception leaves the decoder.

### FirstFrameOnly and MaxFrames

`FirstFrameOnly` returns after the first displayed frame (frame 0 of the full decode, bit for bit). Whether the rest
of the codestream is still scanned for `MaxFrames` is decision 1. `MaxFrames` keeps its 0.8.9 meaning inside the
session (all frames stored in the codestream, displayed or not); the core's own count through `ReservePixels` counts
displayed frames, which is never larger.

### Identify

For animations `Identify` reads every frame header and TOC with `ReadFrameHeaders` (no section decoding, no pixel
work) and reports `FrameCount` = displayed frames and `IsAnimated = FrameCount > 1`, matching `Image.Load` and the
core's `Image.IsAnimated`. It applies `MaxFrames` to the stored frames and throws `ImageFormatException` on a corrupt
frame header or TOC. Stills keep today's header-only `Identify` (`FrameCount = 1`). `JxlLayers.Identify` and
`JxlLayers.Load` keep rejecting animations.

### Support policy

`EnsureImageSupported` no longer rejects animations. Unchanged: noise and splines (0.8.14), so the conformance
`animation_spline` files stay `NotSupportedException`; premultiplied alpha, spot colours, CMYK and float (0.8.15 and
later); preview frames are skipped as today.

### Limits and memory

Working memory per animation is that of a layered still, not of the whole animation: the current frame's buffers
(rewound after the frame), the canvas being produced, and the canvases still held by slots (at most four distinct
ones), all charged to `JxlWorkBudget` (K × `MaxPixels`) before allocation. Displayed frames that leave the session
are owned by the output `Image` and charged by the core through `ReservePixels`. The plugin never holds the previous
displayed frame. Cancellation is checked per frame and inside every stage as today.

### Not in scope

- `Image.OpenFrameReaderAsync` for JPEG XL (needs a core SPI for plugin frame readers; to be raised with the core).
- Frame names and timecodes in any API; animation encoding (0.8.13); splines and noise (0.8.14).

## Tests and corpus

- Corpus (`tests/assets/generate-corpus.py`, cjxl 0.12.0 from Pillow-made inputs): `animation.jxl` (existing, now
  expected to decode), plus `anim-lossy` (APNG, `-d 1`), `anim-crop` (APNG with partial frames, `OVER` blending and
  every dispose op, lossless), `anim-gif` (GIF with transparency and disposal, lossless), `anim-16bit` (16-bit APNG,
  lossless) and `anim-gray` (gray APNG, lossy). Inputs with loop counts, other tick rates, timecodes, names,
  internal zero-duration frames and shown frames that are not saved come from the generator of decision 2.
- Oracle (Category=Oracle, skip without djxl): `djxl --output_frames` to PAM per frame (coalesced), compared frame by
  frame: same count, lossless exact, lossy within 1/255, alpha exact, also with `PreserveBitDepth` (16-bit PAM) and
  `ColorConversion = ToSrgb`. Durations and loop count against `jxlinfo -v` (frame durations in ms, `Num loops`),
  with internal frames removed by the rule above.
- Conformance (ignored corpus, skip when missing): `animation_icos4d`, `animation_icos4d_5`,
  `animation_newtons_cradle` against djxl as above and against their `test.json` durations; `animation_spline` and
  `animation_spline_5` throw `NotSupportedException` naming splines.
- Options and limits: `FirstFrameOnly` (one frame, equal to frame 0, `LoopCount` per decision 3); `MaxFrames` at and
  below the stored frame count; `MaxPixels` just below and at N canvases (Rgba64 counting twice), failing before
  allocation; cancellation before, between and during frames; a truncated animation fails after some frames and leaves
  no live rental (checked build counting pool); 1 vs 16 threads identical; `Identify` `FrameCount`/`IsAnimated` equal
  to `Image.Load`; `IgnoreMetadata`, `ApplyExifOrientation`, `TargetSize` applied to every frame; `JxlLayers` still
  rejects animations.
- Golden: `scripts/golden-hash.sh 0.8.11` at `JXL_GOLDEN_THREADS=1` and `16`: every existing result identical except
  the files that now decode (`animation.jxl` and any fuzz-corpus animations), plus lines for the new files. The golden
  tool hashes every frame and its duration.
- Fuzzing: animated corpus files join the `decode` seeds; short runs of `decode`, `cancel-decode` and `diff-decode`
  (`scripts/fuzz.sh`; the differential harness compares every coalesced frame with djxl's `--output_frames`).
- Package consumer: `scripts/verify-package-consumer.sh` also decodes `animation.jxl` (JIT and Native AOT).
- Speed: still-image paths are unchanged; release notes record the decode time of `animation_newtons_cradle`.

## Results (2026-11-02)

- Code: `JxlDecodeSession.DecodeAnimation` (displayed frames to a sink, `CanBeReferenced` saving, the still path per
  frame for full unsaved Replace frames, `SkipFrames` after `FirstFrameOnly`), `JxlPixelWriter.WriteFrame`,
  `JxlDecoder.DecodeAnimation`/`Duration` and the animation branch of `Identify`. A displayed frame that is also
  saved before the colour transform is decoded twice (once rendered, once for its slot), because the frame decoder
  renders a frame only once; no test file has one. The support policy no longer rejects animations.
- Corpus: 11 animations. cjxl: `anim-lossy`, `anim-gray` (APNG, lossy), `anim-crop` (APNG with dispose and blend
  ops), `anim-gif`; `jxl_anim_gen` (tests/assets/tools): `anim-ticks-loops`, `anim-unsaved`, `anim-single`,
  `anim-16bit`, `anim-vardct-alpha`, `anim-orient6`. corpus.json gains ticks, loops, shown durations (jxlinfo) and
  every frame's 8-bit hash (djxl APNG output; its PAM output ignores `--bits_per_sample`); lossy frames are kept in
  `djxl/<name>-<frame>.png`. libjxl's encoder keeps slot 3 for patches, so the specs use slots 0–2. The other corpus
  files regenerate unchanged except the known non-deterministic `jxl_from_tree` files, which were restored.
- Oracle: every corpus animation and the conformance `animation_icos4d`, `animation_icos4d_5`,
  `animation_newtons_cradle` match djxl frame by frame (lossless exactly, icos4d within 1 in at most 4 samples per
  frame); durations equal `test.json`; `animation_spline(_5)` throw NotSupportedException (splines).
- Tests 717 (642 + 75). Golden against 0.8.11: 1757 results, identical at 1 and 16 threads; only the lines of the 11
  animation files changed (140, all `NotSupportedException` before). The golden tool appends a hash of every frame
  and duration for animations; still lines are unchanged.
- Fuzzing (PC, seed 24, 5 min each): `decode` 2.46 M and `cancel-decode` 609 k inputs, no finding (the `decode`
  target now also sets `FirstFrameOnly` and compares every frame at 1 and 4 threads). `diff-decode` (every frame
  against djxl) 179 k inputs, no mismatch; 3 accept and 2 lenient inputs, none an animation: an invalid red
  chromaticity and a truncated `jxlp` box djxl accepts, and a still image djxl rejects but 0.8.11 decodes too (for
  0.8.16).
- Speed: `animation_newtons_cradle` 157 ms at 1 thread, 135 ms at all cores; djxl about 151 ms.
- Pack and the package consumer (JIT and Native AOT, now also decoding `anim-ticks-loops.jxl`) pass.

## Open decisions (user)

None open. Decided (user, 2026-11-02), each the recommended option:

1. `FirstFrameOnly` reads the remaining frame headers and TOCs without decoding them, so `MaxFrames` limits the stored
   frames and `Identify` and `Load` reject the same files.
2. Inputs cjxl cannot write come from a small C++ dev tool `jxl_anim_gen` on the libjxl 0.12.0 encoder API (source in
   `tests/assets/tools/`, built in `~/.cache` like `jxl_from_tree`, not shipped); the files are committed.
3. `LoopCount` is 0 when the result has one frame, as the core's PNG and GIF decoders do.
