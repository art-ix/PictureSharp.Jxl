# Mutation fuzzing for 0.8.7

Status: released in 0.8.7. Base: `86fbdff` (0.8.6).

0.8.7 starts the fuzzing and resilience series (roadmap in plan.md: 0.8.7 mutation fuzzing, 0.8.8 differential
interoperability against djxl, 0.8.9 resource budgets and failure paths, 0.8.10 long campaigns, 0.9.0 stabilization).
This step adds the fuzzing harness, runs it against every parser and decoder stage, and fixes the findings. It changes
neither the decoded output nor the encoded bytes: the 1469 golden results of 0.8.6 (7f0990ec…) stay identical at 1
and 16 threads, and the two regression inputs add 18.

## What exists

- `JxlCorpusTests.DamagedFiles_FailOnlyWithFormatErrors`: every prefix and the bits of the first 96 bytes of each
  corpus file, but only up to the headers (`JxlHeadersReader`).
- `JxlDecodeTests.Decode_EveryTruncation_IsRejectedAsCorrupt` (3 files) and `Decode_EveryBitFlip_DecodesOrFailsCleanly`
  (7 files), through `Image.Load`.
- These are exhaustive single-bit and truncation sweeps over a fixed corpus. Nothing combines mutations, splices files,
  targets length and count fields, or covers JPEG input (`FromJpeg`), `ToJpeg`, metadata boxes or `Identify` systematically.

## Pass and fail

A run passes when the call returns, or throws `ImageFormatException` or `NotSupportedException`, or
`OperationCanceledException` after its token was cancelled. Everything else is a finding:

- any other exception type, including one wrapped as the inner exception of an `ImageFormatException`. Core
  `Image.Load` wraps decoder exceptions, so the harness unwraps the whole inner chain;
- a run that exceeds the time limit (`--timeout`, default 10 s per input) or the memory limit
  (`DOTNET_GCHeapHardLimit`, `--heap-mb`, default 2 GiB): an `OutOfMemoryException` is a finding;
- a process crash (stack overflow, access violation). With no `unsafe` blocks this can only come from the unchecked
  `Unsafe.Add` reads (see below) or from deep recursion;
- a result that differs between two runs of the same input: decode, `ToJpeg` and `FromJpeg` run at 1 and at 4 threads,
  the second run on buffers the first returned to the pool. A difference shows a read of uninitialized or stale data.
  `FromJpeg` output must also reconstruct the input JPEG byte for byte.

## Harness

Three projects under `tools/`, none packed:

- `PictureSharp.Jxl.FuzzTargets`: the targets and pass rules (`FuzzTargets`), compiled together with the plugin
  sources, as the tests do, so the internal parsers are reachable without `InternalsVisibleTo`. Only this build defines
  `JXL_FUZZ_CHECKED` and `JXL_FUZZ_TRACE`.
- `PictureSharp.Jxl.Fuzz`, the mutation fuzzer (BCL only):
  - `fuzz <target> [--seed S] [--time SEC | --iterations N] [--workers W] [--timeout SEC] [--heap-mb M]`: a supervisor
    with W worker processes. Each input is derived from `(seed, iteration)` with xoshiro256**, so
    `generate <target> --seed S --iteration I` reproduces it without the saved file.
  - A watchdog thread in each worker saves an input that runs too long and ends the process; the supervisor restarts
    the worker after it. After a crash it bisects the 256 iterations since the last progress report for the input.
  - `repro <target> <file>...` runs saved inputs with the full checks and prints the stack trace.
  - Output: `artifacts/fuzz-0.8.7/custom/<target>/{exception,mismatch,hang,crash}/<signature>.{bin,txt,hits}`. The
    signature is the exception type and the first three library frames (for crashes, those of stderr); the smallest
    input is kept, and `.hits` lists every hit.
- `PictureSharp.Jxl.SharpFuzz`, the AFL++/libFuzzer harness (below).

`scripts/fuzz.sh` drives them: `custom`, `afl`, `campaign`, `boundary`, `status` and `repro` (see its header).

### Targets

| Target | Entry | Seeds |
| --- | --- | --- |
| `container` | `JxlContainer.Parse` with metadata and `jbrd`, then every metadata box read (brob decompressed) | corpus `*.jxl` |
| `headers` | `JxlHeadersReader.Read` directly, then `Image.Identify` | corpus `*.jxl` |
| `decode` | `Image.Load` at 1 and 4 threads; `PreserveBitDepth`, `ToSrgb`/`None` and `IgnoreMetadata` from a hash of the input; `MaxPixels` 2^22 | corpus `*.jxl` |
| `entropy` | byte 0 selects: entropy code + 4096 symbols, MA tree, prefix code, context map or hybrid uint; byte 1 is the context count or alphabet | ANS/prefix streams written by `JxlEntropyEncoder` |
| `tojpeg` | `JxlTranscoder.ToJpeg` at 1 and 4 threads | corpus `*.jxl` |
| `fromjpeg` | `JxlTranscoder.FromJpeg` at 1 and 4 threads, then `ToJpeg` back to the same bytes | corpus `*.jpg` |

The JPEG XL targets also take the boundary set below as seeds (`--extra`); seeds above 256 KiB are left out.

Encoder fuzzing (`Save` with random sizes, pixel types and options, then a lossless round trip) moves to 0.8.9, with
the resource budgets (user decision 2026-10-30).

### Mutators

One to four per input, from a seed picked at random:

- bit flip, byte set to a boundary value (0, 1, 0x7F, 0x80, 0xFE, 0xFF) or nudged by ±16, insert, delete, a range
  repeated up to four times, truncation;
- splice: a range from another seed over or into the input;
- container-aware (boxed files): a box size set to 0, 1, too small, one off or too large; two boxes swapped; a box
  duplicated or deleted; the first payload word (jxlp counter, brob type, brand) set to a boundary value;
- codestream-aware (40% of inputs): one or two fields rewritten with 0, all ones, 1, one bit flipped or random bits.
  The fields are the first 4096 `JxlBitReader.ReadBits` calls of decoding each seed (`JXL_FUZZ_TRACE`: size header,
  metadata, ICC, frame header, TOC, group headers), mapped through jxlc/jxlp parts to file bits; 80585 fields over
  the 81 corpus seeds. They are applied before the length-changing mutations.

### Coverage-guided fuzzing (SharpFuzz)

Next to the custom mutator (user decision 2026-10-30). The custom mutator stays the reproducible, dependency-free
baseline. SharpFuzz finds deep paths the random mutations reach only by chance: entropy-coded data, MA trees and
VarDCT/AC strategies.

- `tools/PictureSharp.Jxl.SharpFuzz`, a separate project that is not packed. It references the `SharpFuzz` 2.3.0
  NuGet package (MIT, netstandard2.0, depends on dnlib), and the `SharpFuzz.CommandLine` 2.3.0 local dotnet tool
  (`dotnet-tools.json`) instruments the published `PictureSharp.Jxl.FuzzTargets.dll` only: the plugin sources and the
  targets, not the core or the BCL. The library itself keeps no new dependency, and `ModuleBoundaryTests` and the
  package checks stay as they are.
- The harness must not touch the instrumented assembly before `Fuzzer.OutOfProcess.Run` maps the coverage memory: a
  static constructor run earlier writes coverage into unmapped memory and the process dies (seen in the first smoke
  run). It therefore repeats the target names instead of reading `FuzzTargets.Names`.
- One entry per target: `Fuzzer.OutOfProcess.Run` for AFL++, and `Fuzzer.LibFuzzer.Run` for libFuzzer
  (libfuzzer-dotnet). Both use the target table and pass rules above. Allowed exceptions are caught inside the entry,
  and everything else reaches the fuzzer as a crash.
- AFL++ (4.09c from Ubuntu 24.04, on the PC and the Orange Pi): `afl-fuzz -t <ms> -m none -V <seconds>`, with the
  memory limit set by `DOTNET_GCHeapHardLimit`. Seeds are the exported fuzzer seeds, minimized with `afl-cmin`, plus
  `jxl.dict` (signatures, box types, JPEG markers). One `-M` main instance and `-S` secondaries, each pinned to one core
  of its slot. `AFL_I_DONT_CARE_ABOUT_MISSING_CRASHES` is set while `core_pattern` pipes to apport.
- First PC smoke run (`headers`, 60 s, one instance): 30k execs/s, stability 99.6%, 290 new corpus entries.
- Before the long campaign a 10-minute smoke run on the Orange Pi proves that the instrumented arm64 build gets
  coverage (`afl-showmap` shows edges).
- Crashes from `out/*/crashes` go through `PictureSharp.Jxl.Fuzz repro` (uninstrumented) for the stack trace and
  deduplication, then into the same findings flow as the custom mutator.
- The `JXL_FUZZ_CHECKED` build applies to the instrumented build too, since both use the targets assembly.

### Dimensions and SIMD boundaries

`fuzz.sh boundary` (`PictureSharp.Jxl.Fuzz boundary`): 438 sizes, widths 1–33, 63–65, 255–257 and 2047–2049 against
heights 1, 2, 7, 8, 9, 33, 256 and 257, and the transposed set for widths 1, 3 and 17. Each size is a noisy gradient
with varying alpha, encoded three ways (8-bit lossless e3, 8-bit lossy e7, 16-bit lossless e1) and decoded at one
thread. Lossless round trips must return the source. SIMD exists only on x86 (AVX2/SSE4.1), so the set runs in the
three `verify-simd.sh` modes (native, `DOTNET_EnableAVX=0`, `DOTNET_EnableHWIntrinsic=0`), and the encoded bytes and
decoded pixels must be identical. On arm64 it runs natively (the scalar path). The 1314 files become extra seeds.

Result on the PC (2026-10-30): 1314 encodes identical in all three modes, every lossless round trip exact.

### Unsafe sites

The only unchecked element accesses in src are the `Unsafe.Add` reads and writes of `JxlWeightedPredictor` (Predict,
Update and ErrorWeight; the `MemoryMarshal.Cast` sites are span-checked). They would read out of bounds silently
instead of throwing. With `JXL_FUZZ_CHECKED` each method first indexes every position it will use through the array,
so a wrong position throws `IndexOutOfRangeException`. The release build is unchanged: rewriting the accesses as one
checked/unchecked helper cost ~3% on the 1 MP lossless decode (175.8 → 181 ms, 4 alternating runs), so only
`#if` blocks were added.

## Machines

- Long campaigns run on the Orange Pi 5 (arm64, user decision 2026-10-30). `scripts/fuzz.sh` takes everything as
  arguments: no hardcoded paths. CPU affinity is optional (`--cpus 4-7` for the A76 cores) and SSH-friendly
  (`nohup`, a log file and a status summary from `fuzz.sh status`).
- SIMD differential runs and short smoke runs run on the x86 PC. Speed matrices stay on x86.

## Findings

Each finding gets a minimized input (simple byte-range reduction; proper minimization is in 0.8.10) in
`tests/assets/corpus/fuzz/` and a regression test that runs it through the same pass rules. A fix must keep golden
identical and must not cost measurable time (targeted check, not a full matrix).

## Results

Executions per target (custom mutator: 2 workers; AFL++: main + 1 secondary instance). Orange Pi 5, arm64, A76 cores:

| Target | PC custom, 1 h | Orange Pi custom | Orange Pi AFL++ | AFL++ edges |
| --- | ---: | ---: | ---: | ---: |
| container | 1416 M | 779 M (1 h) | 52–56 M (56 min) | 283 |
| headers | 497 M | 381 M (1 h) | 52–56 M (56 min) | 934 |
| decode | 22.6 M (+62 M after the fix) | 2.3 M (10 min) | 0.13 M (20 min) + 9.3 M (30 min, `--single`) | 7 500–10 900 |
| entropy | 147 M | 21.5 M (10 min) | 12.1 M (20 min) | 912 |
| tojpeg | 477 M | 54.8 M (10 min) | 14.7 M (20 min) | 6 600 |
| fromjpeg | 5.3 M | 0.64 M (10 min) | 0.05 M (20 min) + 2.3 M (30 min, `--single`) | 7 400–7 700 |

`decode` and `fromjpeg` under AFL++ ran ~50 inputs/s per instance, because every input ran a second time at 4 threads
on the instance's single core. `--single` (`JXL_FUZZ_SINGLE=1`) runs each input once there (the `FromJpeg` round trip
stays; the custom mutator keeps the 1 vs 4 thread comparison): 5–13× faster. No hangs, no out-of-memory, no thread
mismatches.

Findings, both fixed with an input in `tests/assets/corpus/fuzz/` and `JxlFuzzRegressionTests`:

- `decode-dc-transformed-channels.jxl` (custom mutator, PC): `JxlVarDctFrame.DecodeDc` read the channel array it
  created before decoding the DC Modular stream. Inverse RCT, palette and squeeze replace or resize channels, so a DC
  stream with transforms read stale channels: `IndexOutOfRangeException` here, and possibly wrong DC values in a
  valid file. It now reads the image's channels after `Decode` checked their sizes.
- `decode-invalid-chromaticities.jxl` (AFL++ `--single`, Orange Pi, 15 inputs): custom primaries or white point
  outside the CIE range were rejected as `ImageFormatException` with the core's `ArgumentException` inside. The
  message now carries the core's text without an inner exception.

## Done when

- every target has run its campaign on the Orange Pi with no open findings
  (user decisions 2026-10-30: 1 h per target on the x86 PC, all targets in parallel with 2 workers each; on the
  Orange Pi first planned as 3 h per target, then shortened once AFL++ coverage had plateaued on `container` and
  `headers` (283 and 934 edges, no new path for 10–14 min after 56 min): 30 min per target, 10 min custom mutator +
  20 min AFL++, two targets at a time on 2 A76 cores each);
- the SIMD boundary set matches across native/sse41/scalar;
- tests and golden pass at 1/-1 threads, and the package and the JIT/AOT consumers pass.

## Decisions

Decided (user, 2026-10-30): encoder fuzzing in 0.8.9, six targets in 0.8.7; engine — the custom mutator and
SharpFuzz + AFL++; campaigns — 1 h per target on the x86 PC (all targets in parallel), on the Orange Pi 30 min per
target (10 min custom + 20 min AFL++, two targets at a time; `container` and `headers` had already run 1 h custom and
56 min AFL++ under the earlier 3 h plan).
