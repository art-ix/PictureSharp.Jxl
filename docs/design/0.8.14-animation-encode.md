# Animation encode for 0.8.14

Status: implemented (2026-11-02), not committed. Base: `4d9cda0` (0.8.13 + README). Decisions 1a, 2a, 3a (user, 2026-11-02).

Goal: `SaveAsJxl` writes every frame of an `Image` with `FrameCount > 1`, and `JxlFormat.FrameEncoder` makes
`Image.CreateFrameWriter` work for JPEG XL, one canvas at a time. `Image.Load` and `Image.OpenFrameReaderAsync` read
the result back with the same pixels (lossless: exact; lossy: within 1/255 of djxl, alpha exact), durations and loop
count. Still images (one frame) stay byte-identical to 0.8.13. Today the encoder silently writes only the root frame;
that ends here.

## Core contract (0.9.1)

- `IImageFormatFrameEncoder.Open(Stream, ImageFrameSequenceInfo, EncoderOptions, ImageMetadata)` returns an
  `ImageFrameSink`; `WriteAsync(frame, duration, ct)` per frame, `CompleteAsync` at the end, `DisposeAsync` always.
- The core validates options before the file is created, checks every frame's size and pixel type, converts frames the
  sink does not accept (`SupportsPixelType`), counts frames against the declared `FrameCount`, and deletes incomplete
  path output. A writer that declares a single frame uses `Encoder`, not the frame encoder.
- `RequiresSeekableOutput` stays false: the design below writes forward only.

## Design

1. **One code path.** A new internal `JxlAnimationWriter` encodes frame by frame. `JxlFrameSink` wraps it for
   `CreateFrameWriter`; `JxlEncoder.Encode` uses it when `image.FrameCount > 1` (frames in order, `image.LoopCount`).
   The still path is untouched.
2. **Headers at the first frame.** `Animation` header with tps 1000/1, `num_loops = LoopCount`, no timecodes;
   colour encoding, ICC, orientation, bit depth (8 for `Rgba32`, 16 for `Rgba64`, no 8-bit intermediate) as for stills.
   The colour channels (gray or RGB) and the alpha channel must be fixed before the first frame (decision 2).
3. **Durations.** `ticks = round(duration / 1 ms)` (midpoint away from zero), 0 … 2^32−1; larger values throw
   `NotSupportedException` naming the limit. Zero-duration frames: decision 1.
4. **Changed rectangle.** The first frame is a full Replace frame. Each later frame is cropped to the bounding box of
   pixels that differ from the previous source frame (all four channels compared exactly), blended with Replace over
   reference slot 1 (`blend_source = 1`), and every frame except the last is saved to slot 1 after blending, so the
   decoder composes the full canvas (0.8.10 code). The writer keeps a copy of the previous source canvas (one canvas
   of memory). Lossy frames are compared on source pixels, as cjxl does with APNG/GIF rectangles; the unchanged area
   shows the earlier decoded pixels. Patches keep slot 3 (`kPatchFrameReferenceId`), so they do not collide. (Slot 0 of the proposal does not work: a frame with a duration is saved only when `save_as_reference != 0`, libjxl `CanBeReferenced`.) A frame
   identical to the previous one: decision 3.
5. **Hold back one encoded frame.** `is_last` sits in the frame header and changes its length (the save fields are
   omitted for the last frame). The writer therefore keeps the last encoded frame as header fields + TOC sizes + the
   byte-aligned section data, and writes it when the next frame arrives (`is_last = false`) or at `CompleteAsync`
   (`is_last = true`, header and TOC written again, sections copied). Memory: one compressed frame.
6. **Output.** Without metadata boxes and at level 5, a raw codestream is written piece by piece. Otherwise a container
   (`ftyp`, `jxll` if needed, Exif/XMP boxes, possibly `brob`) followed by one `jxlp` box per written piece (the first
   holds the headers and ICC), the last one with the high bit set; the decoder already accepts this layout. The
   conformance level comes from the canvas size, which is known at the first frame.
7. **Options.** Distance, effort, `Lossless`, `MaxDegreeOfParallelism` and metadata options apply to every frame as
   for stills. No new public option. Cancellation is checked per frame and inside each frame as today; disposal before
   `CompleteAsync` releases the pooled buffers and writes nothing more.
8. **Budget.** The encoder has no decode budget; the working memory is one frame's encode buffers + the previous
   canvas + the held-back compressed frame.

## Decisions for the user

1. **Zero-duration frames.** (a, recommended) Keep 0 ticks: in JPEG XL a non-last zero-duration frame is a layer
   merged into the next one, so viewers show the same animation, but `Image.Load` returns fewer frames than were
   written (as cjxl does with 0-delay APNG frames). (b) Write at least 1 ms, so every written frame is decoded as a
   frame, at the cost of 1 ms per such frame.
2. **Gray and alpha for sequences.** (a, recommended) `SaveAsJxl` scans all frames (they are in memory) and decides
   gray/alpha like stills; `CreateFrameWriter` cannot see later frames, so it writes RGB with alpha unless a gray ICC
   profile is given (then a non-gray frame throws `NotSupportedException`). Decoded pixels are the same either way;
   an opaque alpha plane costs a few bytes per frame. (b) Both paths always write RGB with alpha (simpler, small size
   cost for gray or opaque `Image.Save` animations).
3. **Identical consecutive frames.** (a, recommended) Add the duration to the held-back frame instead of writing a
   new one, as the core GIF encoder does: the same animation with fewer frames. (b) Write a 1×1 Replace frame so the
   frame count is kept.

## Tests and checks (planned)

- Round trip of every animated corpus file (decode → encode lossless → decode) exactly equal frames, durations
  (ms-rounded) and loop count, via `Image.Save` and via `CreateFrameWriter`, both read back by `Image.Load` and the
  frame reader; djxl decodes our output to the same frames (oracle, lossless exact, lossy within 1/255).
- Cropping: frames changing one pixel, a corner, everything, nothing; alpha-only changes; Rgba64; gray ICC.
- `is_last` hold-back: 2 frames, unknown frame count, `CompleteAsync` without frames (core rule), disposal mid-way,
  cancellation inside a frame, non-seekable output, container with Exif/XMP/brob and level 10.
- Sizes against cjxl 0.12.0 on the same frames (APNG input), lossless and lossy; speed per frame like stills.
- Golden: every still result identical to 0.8.13 at 1 and 16 threads; new golden entries for animation output.
- Fuzz: short runs of a new `encode-frames` target (random frame sequences, round trip through the decoder).
- Package consumer JIT/AOT writes a short animation with `CreateFrameWriter`.

## Deviations and results

- Slot 1 instead of 0 (see design point 4). The core's writer-side `ImageFrameSequenceInfo` carries no pixel type in
  0.9.1, so the frame writer takes the bit depth of the first frame; 8-bit frames of a 16-bit sequence are widened
  exactly (×257). Options are validated in `Open` by building a writer on the unwritten stream.
- The held-back frame is rewritten by reading its header and TOC back (`JxlFrameHeaderReader`, `JxlTocReader`) and
  writing them again with `JxlHeaderWriter.Frame`, which now writes durations, origins and the blend source of partial
  frames and the `save_before_ct` rule of the reader. Still-image headers are bit-identical.
- Durations beyond 2^32 − 1 ms throw `NotSupportedException` (anim-16bit.jxl: 2^32 − 1 ticks at 100 tps).
- Checks: tests 927/927 (27 new in JxlAnimationEncodeTests incl. djxl oracle); golden vs 0.8.13: 70 lines, only the
  lossless/losslessC/lossy(16) encodes of the 10 multi-frame corpus files, t1 == t16; fuzz `encode-frames` seed 29
  117,596 inputs clean; pack + consumer JIT/AOT (writes anim-ticks-loops with the frame writer) pass.
- Sizes vs cjxl 0.12.0 on APNG of the same frames (ours/cjxl): icos4d 128×128×48 d0 0.993, d1 0.951; newtons_cradle
  480×360×36 d0 0.330, d1 0.347; anim-long d0 0.249; tiny corpus files up to +73 bytes lossless.
