# Differential interoperability for 0.8.8

Status: prepared for release as 0.8.8 (2026-10-31). Base: `ca07f21` (0.8.7).

0.8.8 is the second step of the fuzzing and resilience series (roadmap in plan.md: 0.8.7 mutation fuzzing, 0.8.8
differential interoperability against cjxl/djxl, 0.8.9 resource budgets, failure paths and encoder fuzzing, 0.8.10
long campaigns, 0.9.0 stabilization). 0.8.7 checked that every input decodes or fails cleanly; 0.8.8 checks that the
result agrees with libjxl. It changes neither the decoded output nor the encoded bytes unless a finding needs a fix:
golden stays identical to 0.8.7 (1487 results) at 1 and 16 threads.

## What exists

- `JxlOracleTests`, `JxlDecodeOracleTests`, `JxlEncodeOracleTests`: fixed corpus compared with djxl/cjxl found through
  `JXL_TOOLS` or `PATH`. Modular decodes are bit-exact, VarDCT within 1, ICC byte-identical to djxl.
- `JxlJpegTests`: `FromJpeg`/`ToJpeg` round trips on the corpus JPEGs.
- 0.8.7 harness: `tools/PictureSharp.Jxl.Fuzz` (supervisor, workers, reproducible inputs from `(seed, iteration)`),
  `tools/PictureSharp.Jxl.FuzzTargets`, `scripts/fuzz.sh`, the boundary set and the Orange Pi setup.
- Tools on the PC (`~/.local/bin`): cjxl, djxl, jxlinfo, jxltran, butteraugli_main, ssimulacra2, all v0.12.0.

Nothing compares generated or mutated files against libjxl, and nothing checks the files our encoder writes with djxl
beyond the fixed oracle cases.

## Reference tools

- The tools must be libjxl v0.12.0 as pinned in `scripts/reference-lock.json` (commit `a7a9c787…`). The installed
  binaries (the static `jxl-linux-x86_64` release assets) report `v0.12.0 4128790`: that is the release workflow's
  merge of `8d2a6d8` ("Fix `publish_release_assets`") into `a7a9c787`, which changes only
  `.github/workflows/release.yaml`. The library sources are the pinned ones, so the release binaries are used.
- Each campaign prints the version lines and SHA-256 prefixes of cjxl, djxl and ssimulacra2 (ssimulacra2 has no
  version option).
- The same tools are built for arm64 on the Orange Pi; x86 and arm64 djxl output may differ in VarDCT floats, so
  the reference is always the djxl of the same machine.

## Pass and fail

### Decode (ours vs djxl)

- Inputs: corpus files; files from cjxl with options drawn from a seed (effort 1–9, distance 0–15, `--modular`,
  progressive/`-p`, `--resampling`, `--patches`, `--dots`, `--gaborish`, `--epf`, alpha, 8/16-bit, gray, animation
  first frame within supported scope); 0.8.7 mutated inputs.
- Both decode with the orientation applied (djxl always undoes it) to 8 bits; XYB images outside sRGB with ToSrgb
  against `djxl --color_space=RGB_D65_SRG_Rel_SRG` (gray: `Gra_D65_Rel_SRG`), as `JxlDecodeOracleTests`.
- Pixels: identical when every frame is Modular without XYB at up to 8 bits; every sample within 1 for YCbCr
  (recompressed JPEG) frames, as `JxlJpegTests`; otherwise `JxlDecodeTests.Tolerance` (within 1, at most 0.1% of the
  samples different, at least 16 in small images; a gray pixel counts once).
- Acceptance: both decoders accept or both reject. A file djxl decodes and we reject (or the reverse) is an `accept`
  finding. `NotSupportedException` (animation, float, noise) passes, and inputs rejected for `MaxPixels` or
  `MaxMetadataBytes`, which libjxl does not have, are not compared.
- Metadata: the ICC profile of `ReadMetadata` byte for byte as `djxl --orig_icc_out`. Exif and XMP are not compared
  yet (djxl does not write them out); orientation is covered by the pixel comparison.

### Encode (ours vs djxl)

- Input bytes: flags (lossless, 16-bit, alpha, gray, ICC, one of 8 patterns), effort 1–9, distance 0.5–15, size up
  to 320×320, then noise. 256 seeds cover every flag combination.
- Lossless: djxl output (16-bit PNG for 16-bit sources) identical to the source; an attached ICC profile (corpus
  `icc-profile.jxl`) is what `djxl --orig_icc_out` extracts.
- Lossy: djxl output equal to our own decode within the tolerance above.
- Quality, for 8-bit opaque sources of at least 64×64, against cjxl at the same distance and effort (cjxl `-e 7` for
  efforts 8 and 9, which behave as 7 without butteraugli iterations, plan.md; against cjxl -e 9 our e9 scored about
  6 points lower at the same size): a finding when
  ssimulacra2 is more than 5 points lower without the file being 10% smaller, or the file is more than 1.25× larger
  (cjxl at least 1 KiB) without scoring 2 points more. A trade of size for quality is not a finding (two such hits:
  7 points lower at 11% smaller). Not compared when cjxl scores below 30 (noise at high distances). ssimulacra2 ignores alpha, and 16-bit or tiny images make both numbers
  meaningless. Butteraugli is not used: one metric suffices for a threshold, and it is several times slower.
- `EditMetadata` is not exercised here yet.
- Full encoder fuzzing (random sizes, pixel types, options) stays in 0.8.9.

### JPEG reconstruction

- `FromJpeg` output → `djxl` to JPEG: byte-identical to the input JPEG, also when cjxl refuses the JPEG.
- `cjxl --lossless_jpeg=1` output → our `ToJpeg`: byte-identical to the input JPEG.
- When libjxl does not round-trip a JPEG itself (cjxl's file fails in djxl too), our rejection passes, and our
  acceptance is `lenient` if this library reconstructs its own file exactly. A format error in `ToJpeg` of our own
  `FromJpeg` output is a `mismatch` (the 0.8.7 `fromjpeg` target counted it as a pass).
- `ToJpeg` of a file with `jbrd` against djxl: the same bytes. djxl falls back to pixels when it cannot reconstruct
  ("Decoded to pixels."); then our pixel decode must match djxl's within 1.
- JPEG set: baseline and progressive, restart markers, 4:4:4/4:2:2/4:2:0/4:1:1, gray, CMYK/Adobe where supported,
  APPn/COM markers and trailing data. JPEGs libjxl refuses to recompress must be refused by us too.

### Lenient results

Where this library accepts what libjxl rejects and the result can still be checked against libjxl, the input is
saved as `lenient`, which is not a defect by itself:

- djxl fails on a damaged metadata box (for example a brob that does not decompress), which this library skips: djxl
  decodes the file without its metadata boxes, and the pixels agree;
- djxl cannot convert to sRGB with its colour management (damaged ICC profile), while ToSrgb renders XYB as sRGB
  directly: nothing to compare;
- djxl only decodes to pixels where this library reconstructs a JPEG: the pixels agree;
- cjxl refuses a JPEG this library transcodes: djxl reconstructs our file byte for byte.

## Harness

- `tools/PictureSharp.Jxl.FuzzTargets/DiffTargets.cs`: the four targets `diff-decode`, `diff-encode`, `diff-tojpeg`
  and `diff-fromjpeg`, run by the 0.8.7 mutation fuzzer (`FuzzTargets.Run` hands `diff-*` to them). The tools run
  once per input with `--num_threads=1` and a 20 s limit; the libjxl process start dominates, so AFL++ is not used.
- Every fourth iteration is an unchanged seed, in turn, so that valid files are compared too. Seeds: the corpus
  (`diff-tojpeg`: files with a `jbrd` box; `diff-fromjpeg`: `*.jpg`), and generated parameter blobs for `diff-encode`.
- Finding kinds: `mismatch`, `accept`, `lenient`, `quality`, `tool` (a libjxl tool timed out) and the 0.8.7 kinds.
  Signatures of differential findings are the message with numbers and quoted box types left out.
- `scripts/fuzz.sh diff [--time SEC] [--workers N] [--targets ...]`: all four targets in parallel, `--timeout 60`,
  output in `artifacts/fuzz-0.8.8`; `status` and `repro` as in 0.8.7. `PictureSharp.Jxl.Fuzz render <jxl> <png>`
  writes this library's decode as the targets compare it, `transcode` runs FromJpeg/ToJpeg, and `JXL_DIFF_KEEP=1`
  keeps the files of each run (triage).
- Rates on the PC (i5-12500H, 2 workers per target): diff-decode ~750, diff-tojpeg ~800, diff-fromjpeg ~310,
  diff-encode ~75 inputs/s.

## Machines

- Campaigns and quality thresholds on the x86 PC only. The Orange Pi 5 campaign is dropped for 0.8.8 (user decision
  2026-10-31: the Pi is not available); long differential runs can join the 0.8.10 campaigns.

## Findings

Each finding gets a minimized input in `tests/assets/corpus/fuzz/` (or `corpus/diff/`) and a regression test that
compares against a stored djxl result, so CI does not need libjxl. Fixes keep golden identical unless the finding is
a wrong output; a changed golden result is listed in the release notes.

## Results

PC runs 2026-10-31: smoke runs (90 s and 150 s per target, 2 workers), then 10 min per target with 3 workers,
seed 1 (1.17 M inputs), seed 2 (1.17 M) and seed 3 (1.12 M). The corpus decodes like djxl. After the fixes below
the saved `mismatch` inputs of seeds 1 and 2 pass, and seed 3 found no `mismatch` or `quality` finding; `accept`
(33 signatures) and `lenient` (4) remain.

Fixed:

- 8-bit dithering with orientation: libjxl undoes the orientation while writing 8-bit output and mirrors before it
  dithers: from the bottom row when the orientation flips vertically (3, 4, 6, 7; `ProcessRow` flips `ypos`) and from
  the last column when it flips horizontally (2, 3, 7, 8; `FlipX` reverses the row and `xstart`); a transpose comes
  after. With `ApplyExifOrientation` this library now does the same (`JxlPixelWriter.DitherFlip`; a horizontally
  mirrored row is written by the scalar loop). Before, about 25% of the samples of such images differed by 1
  (`transcoding/metadata-0.jxl`: 764 of 3276, now 2). Found on `metadata-brob.jxl` with its bit depth mutated to 12
  (orientation 6, and 8 with seed 2); these inputs and djxl's renderings are in `corpus/diff`, tested by
  `JxlDiffRegressionTests` with the two recompressed JPEGs. Golden (no orientation applied) is unchanged.

- Extra zero runs beyond the block: cjxl records `jbrd` zero runs that cover more than the zeros left in a block,
  and djxl then writes no end of band. `ToJpeg` rejected such files ("Invalid JPEG extra zero runs"); it now writes
  them as libjxl does (`JxlJpegWriter.EncodeBlock`). Input: `corpus/diff/tojpeg-extra-zero-runs.{jxl,jpg}`.
- JPEG DC values beyond ±2047: `FromJpeg` accepted them and wrote a file whose reconstruction fails
  ("Reconstructed JPEG DC coefficient out of range"). cjxl accepts them too, and its file fails in djxl or
  reconstructs to other bytes. `JxlJpegReader` now rejects such JPEGs ("JPEG DC coefficient out of range"), and the
  `fromjpeg` targets treat a failing reconstruction of their own output as a mismatch. Input:
  `corpus/diff/fromjpeg-dc-out-of-range.jpg` (`JxlDiffRegressionTests`).

This library decodes what libjxl rejects, not verified automatically (`accept`, 2 inputs):

- `jxlp-v1-out-of-order.jxl` with the size of its last box set to 0 (to the end of the file, which ISO BMFF allows):
  the same file; djxl fails.
- `lossy-e1.jxl` with one bit set that makes a header field read 1 instead of 0; by the trace it is the extension
  selector at the end of the loop filter bundle (mask 1, extension size 0, so no bits skipped). The frame headers
  this library reads are identical to the original's and the image decodes as before, while djxl fails. libjxl's
  extension handling (`fields.cc`) reads the same; the cause on libjxl's side needs a debug build (open).

Not a defect of this library:

- ToSrgb of images above 8 bits differs from djxl by 1 in about 20% of the samples: the core decodes them with
  `PreserveBitDepth`, converts and rounds to 8 bits without dithering (`ImageDecodeService.ReduceToRgba32`), while
  djxl dithers. The plugin cannot tell that the caller asked for 8 bits. The 16-bit output matches djxl (118 of 9216
  samples by 1); the target compares such decodes with djxl's 16-bit output rounded the same way. Dithering in the
  core's reduction would be a core change.

This library rejects what libjxl accepts (`accept`; kept and documented, user decision 2026-10-31):

| Area | Messages | Notes |
| --- | --- | --- |
| Container | `Truncated '<box>' box`, `Truncated box header` | a box that runs past the end of the file, or garbage after the codestream, which libjxl never reads |
| Container | `The jxlp box index … is out of order` | libjxl ignores the `jxlp` counter |
| Container | `Invalid box size`, `Signature box inside the file`, `The ftyp box must be the second box`, `A jxlp box is too small to contain its index`, `A jxlp box follows the last jxlp box` | libjxl reads only what it needs |
| Codestream | `Non-zero padding bits in the codestream` | libjxl does not check padding |
| Colour | `Invalid red primary chromaticity` | libjxl decodes out-of-range custom primaries |
| JPEG reconstruction | undefined table, scan parameters/component, progressive scan, overlapping scans, quantization entry, DC coefficient range, EXIF offset, APP marker mismatch, reset/zero-run position, frame/image incompatible with the data | djxl writes whatever `jbrd` describes |
| JPEG input | `Invalid JPEG ICC chunk sequence`, `Missing JPEG component DC scan`, `Invalid JPEG scan parameters`, `Invalid progressive JPEG scan` | cjxl transcodes such JPEGs |

## Done when

- every diff target has run its campaign on the PC with no open `mismatch` findings, and every `accept` finding
  falls in a documented area;
- the JPEG set reconstructs byte for byte in both directions;
- tests and golden pass at 1/-1 threads, and the package and the JIT/AOT consumers pass.
