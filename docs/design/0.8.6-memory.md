# Memory use for 0.8.6

Status: released in 0.8.6. Base: `d3844fb` (0.8.5).
Measurements: [speed.md](../benchmarks/speed.md#memory-use-086) and [memory-0.8.6.json](../measurements/memory-0.8.6.json).

0.8.6 reduces the peak memory and the allocations of large decodes, encodes and JPEG reconstruction (user decision,
2026-10-30). Output is unchanged: decoded pixels and encoded bytes are identical to 0.8.5 (golden: 1469 results, SHA-256
7f0990ec…, at 1 and 16 threads). There are no API changes.

## Method

- **Allocation sampling**: `dotnet-trace` with the runtime's GC provider at verbose level (`GCAllocationTick`, one
  sample per ~100 KB, with stacks), summed by type and by the first PictureSharp.Jxl frames with a small TraceEvent
  tool. This gives where bytes are allocated, including pool misses.
- **Pooled peak**: an instrumented build that records every `JxlPooledBuffer` rental with its call site and keeps the
  set of live rentals at the moment their total peaks.
- **Peak RSS**: `/usr/bin/time` around the speed harness, as the 0.8.5 matrix records it, plus a startup hook that
  samples RSS and the GC heap every 2 ms.

### Peak RSS of the speed harness

The harness's peak RSS mostly measures the GC's large-object budget, not the library. The pixel buffer of a decoded
image (48 MB for 12 MP, allocated by PictureSharp) and every large temporary go to the large object heap, which is only
collected by gen-2 collections. Sampling the 12 MP JPEG-reconstructed decode showed the heap growing by the garbage of
each run until a collection, and the process peak followed the number of runs that fit in the warm-up time. Cutting
that decode's allocations from 245 to 55 MB per image left the harness peak at ~0.9 GB, because only fewer
collections ran.

The harness therefore has an opt-in `JXL_COLLECT=1` (`scripts/measure-paired.py --collect`): a full, compacting
collection before every operation, outside the timing. Peak RSS is then that of one operation: runtime, live data,
the operation's own garbage and buffers kept by the shared array pool. Both builds of a `--collect` matrix use the
0.8.6 harness (`artifacts/perf-0.8.6/build.sh base v0.8.5` builds the 0.8.5 library with it). The standard matrix
against the frozen 0.8.5 harness build records allocations, time and the default peak RSS as before.

### 0.8.5 profile (12 MP, one thread)

| Case | Allocated / op | Peak RSS (collect) | Where |
| --- | ---: | ---: | --- |
| decode, JPEG reconstructed (4:2:0) | 245 MB | 329 MiB | chroma upsampling 147 MB (half-height then full-height planes), `DcBucket` closures 36 MB, output 48 MB |
| JPEG reconstruction | 120 MB | 140 MiB | `DcBucket` closures 36 MB, coefficients 36 MB, scan bit buffer growth 9 MB |
| encode lossless e7 | 1002 MB | 1193 MiB (1580 at 16 threads) | colour transform copy 146 MB, planes 146 MB, per-group weighted errors 146 MB, token storage doubling ~130 MB plus ~290 MB live, pool misses |
| encode lossy d1 e7 | 410 MB | 962 MiB | XYB image, its clone for the sharpness search, reconstruction planes and coefficients (192 MiB each), AQ masks 96 MB |
| decode 16-bit lossless e7 | 363 MB | 369 MiB | output 97 MB; per-group trees: list growth, filtered trees, alias tables (~200 MB) |

`ArrayPool<T>.Shared` keeps one array per size bucket per thread plus a few per core. Hundreds of same-size rentals
that are all alive at once (per-group crops, errors and tokens of a 12 MP image) mostly miss the pool: they are
allocated on every operation and dropped on return.

## Changes

| Change | Effect |
| --- | --- |
| `DcBucket` counts thresholds in a loop instead of `Count(lambda)` per block | −36 MB per 12 MP JPEG decode or reconstruction |
| `MaxHShift`/`MaxVShift` loop over the chroma modes instead of LINQ | no enumerator per block (VarDCT decode, AC tokenizer) |
| 4:2:0 chroma upsampled in one pass (`UpsampleChroma2x2`) into pooled planes, in row bands | no half-height plane; −147 MB per 12 MP JPEG decode |
| Subsampled YCbCr frames without later stages render rows on demand (`JxlColorRows`/`JxlYCbCrRows`): the pixel writer upsamples chroma and converts YCbCr per row band | no full-resolution chroma planes: 12 MP JPEG decode peak 329 → 184 MiB, faster at 16 threads |
| Lossless encoding applies the colour transform to the group crops (its own copies) instead of a full transformed copy | −146 MB allocated and live at 12 MP |
| Token storage sized once from the stream's pixel count (one token per pixel) | no doubling and copying |
| The weighted errors of the tree learning scan are recorded in the stream's token value storage (`JxlTokens.ValueStorage`); tokenization keeps a copy of the previous row and replaces a row's errors with its tokens | no error planes: −146 MB live and allocated at 12 MP |
| Lossless input planes rented from the encode's working buffers | no per-encode 146 MB allocation |
| The lossy encoder releases its pooled image after quantization; the sharpness search's reconstruction reuses it | −192 MiB peak at 12 MP |
| AQ: the per-pixel mask intermediate is pooled, the blurred mask comes from the encode's buffers | −96 MB allocated at 12 MP |
| Modular decoding: `InitAliasTable` uses stack scratch instead of three arrays and two stacks per histogram; tree filtering uses pooled scratch and an array queue; tree reading grows a pooled buffer | 16-bit e7 decode −118 MB, 8-bit e7 −53 MB per 12 MP image |
| JPEG reconstruction: coefficients pooled until the JPEG is written; the scan writer hands whole bytes to the output instead of growing its buffer | −80 MB allocated per 12 MP image |

Every change keeps the arithmetic and its order: the fused and row-band chroma paths perform the same multiplications
and FMAs as the separable passes (`JxlMemoryTests` compares them with the frozen scalar baseline for 4:2:0, 4:2:2 and
4:4:0 at odd sizes and bands starting on any row), and the encoders produce the same tokens.

## Results

Per operation (`--collect` matrix, 12 MP, 1 / 16 threads); the full tables and the standard matrix are in
[speed.md](../benchmarks/speed.md#memory-use-086):

| Case | Allocated (MB) | Peak RSS (MiB) | Time |
| --- | --- | --- | --- |
| decode, JPEG reconstructed | 244 → 53 / 244 → 55 | 332 → 180 / 375 → 235 | −10% / −45% |
| JPEG reconstruction | 118 → 38 / 131 → 51 | 143 → 132 / 197 → 193 | −3% / −7% |
| encode lossless e7 | 976 → 576 / 567 → 111 | 1192 → 864 / 1593 → 1035 | ±0% |
| encode lossy d1 e7 | 376 → 282 / 200 → 91 | 959 → 817 / 994 → 847 | −3% / ±0% |
| decode 16-bit lossless e7 | 341 → 170 / 341 → 171 | 369 → 351 / 441 → 442 | −0.5% / −8% |

Speed did not regress: two 16-thread increases of the standard matrix were thermal and GC-timing noise (rechecked
cooled below 60 °C: ±0.1%). `measure-paired.py --cool-below C` waits for the CPU package before every process.

## Not done

- **Peak RSS of the default harness**: still dominated by output images the GC has not collected yet (see above). An
  application decoding many images sees the same; `GCSettings`/`GCConserveMemory` or disposal-aware pixel buffers in
  PictureSharp are outside this plugin.
- **Lossless encoding** still holds the input planes, the group crops and 8 bytes of tokens per pixel at once; tokens
  could be narrowed (16-bit contexts) or crops avoided with strided channels. Both need wider changes.
- **Pool misses** of many same-size group buffers remain allocations per operation (they are live at once).
- **Modular decoding** allocates small per-group objects (entropy codes, filtered trees); they are gen-0 garbage.
